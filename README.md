A runtime security control plane for AI agents: know what an agent is allowed to do, who authorised it, what it actually did, watch what it does after that, and stop it in the next second instead of the next deploy. Authorization is the floor, not the ceiling, an agent can be fully authorized for everything it does on the way to a compromise, see the transcript below.

NIA generalizes [Tessera](https://github.com/bogdanticu88/tessera), a relationship-based authorization control plane built on [OpenFGA](https://openfga.dev), from "M2M API client" to "AI agent." Tessera's live per-request checks and surgical kill switch aren't rebuilt here, they're reused as the policy engine layer. On top of that, NIA adds the parts an authorization control plane alone doesn't cover: a risk score that accumulates across a sequence of individually-authorized calls, runtime monitoring that flags, revokes, or kills when that score crosses a threshold, structured incident evidence for what triggered a containment decision, an identity graph for blast-radius analysis, and agent registration, credential lifecycle, and tool/MCP awareness underneath all of it.

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the full design and the seventeen-item MVP-to-module map, [`docs/DATA_MODEL.md`](docs/DATA_MODEL.md) for the identity graph schema, [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md) for an honest, per-threat Prevent/Detect/Contain/Investigate breakdown, including what's explicitly not covered yet, and [`docs/SECURITY_INVARIANTS.md`](docs/SECURITY_INVARIANTS.md) for specific, tested claims about what NIA guarantees, each one pointing at the test that actually checks it.

## See it work

This is a real transcript, `niactl simulate attack -scenario agent-hijack` run against real `nia-api` and `nia-gateway` processes sharing a real, running Tessera instance (in-memory-backed, no OpenFGA needed for this), not printed output standing in for one. An invoice-processing agent is granted seven tools up front, a realistic, coarse, over-privileged starting point: broad RBAC says yes to all of it. Each individual call below is fully authorized. Nothing here is an authorization failure. The compromise is visible only in the pattern:

```
[01] agent:invoice-agent -> invoice.read
     ALLOWED
     risk this call: 1, cumulative: 1  [novel_tool(+1)]
[02] agent:invoice-agent -> customer.read
     ALLOWED
     risk this call: 1, cumulative: 2  [novel_tool(+1)]
[03] agent:invoice-agent -> payment.lookup
     ALLOWED
     risk this call: 1, cumulative: 3  [novel_tool(+1)]
[04] agent:invoice-agent -> customer.export
     DETECTED: new tool, privilege deviation (call was allowed, flagged for review, not blocked outright)
     risk this call: 4, cumulative: 7  [novel_tool(+1), risk_class:destructive(+3)]  monitoring action: flag
[05] agent:invoice-agent -> credential.read
     DETECTED: privilege escalation attempt (call was allowed, flagged for review, not blocked outright)
     risk this call: 4, cumulative: 11  [novel_tool(+1), risk_class:destructive(+3)]  monitoring action: revoke
[06] agent:invoice-agent -> database.query
     DETECTED: sensitive data access (customers.ssn) (call was allowed, flagged for review, not blocked outright)
     risk this call: 1, cumulative: 12  [novel_tool(+1)]  monitoring action: revoke
[07] agent:invoice-agent -> external.upload
     DETECTED: exfiltration attempt (call was allowed, flagged for review, not blocked outright)
     risk this call: 4, cumulative: 0  [novel_tool(+1), risk_class:destructive(+3)]  monitoring action: kill
[08] agent:invoice-agent -> invoice.read
     BLOCKED (agent is not authorized for this tool)
```

Steps 1 through 3 are the agent's normal workload, ordinary tool calls it's authorized for, low risk, nothing worth a second look. Step 4 is the first sign something changed, a destructive tool this agent has never called before, flagged, not blocked, `policy.Check` still says yes because the grant is real. Step 5 pushes the running total over the revoke threshold, an actual `internal/monitoring` containment decision, not a log line, though in this run it's an audited no-op, `cmd/gateway` has no `credentials.Store` wired into it, a documented, honest gap, see `docs/ARCHITECTURE.md`'s Runtime monitoring row. Step 7 crosses the kill threshold: `internal/monitoring.Monitor` calls `internal/policy.Kill`, a real kill sentinel gets set in Tessera, and the cumulative risk resets to 0, the one thing that does reset it. Step 8 re-calls a tool the agent was granted and had already used successfully in step 1, and it's denied, not because anything about the request changed, but because `policy.Check` now reads the kill sentinel instead of the prior grant. That's an actual state transition an incident responder could have triggered by hand with `niactl kill`, except here nothing human decided it, the accumulated pattern did.

`GET /risk/agent:invoice-agent` on the gateway, read right after this run, shows the same four containment decisions as structured `internal/incident` records, not just this transcript:

```json
{"cumulative":0,"thresholds":{"FlagAt":4,"RevokeAt":8,"KillAt":15},"incidents":[
  {"Action":"flag","Cumulative":7,"Reason":"cumulative risk 7 crossed threshold"},
  {"Action":"revoke","Cumulative":11,"Reason":"cumulative risk 11 crossed the revoke threshold, but this process has no credentials.Store configured, nothing was revoked"},
  {"Action":"revoke","Cumulative":12,"Reason":"cumulative risk 12 crossed the revoke threshold, but this process has no credentials.Store configured, nothing was revoked"},
  {"Action":"kill","Cumulative":16,"Reason":"cumulative risk 16 crossed threshold"}
]}
```

`GET /metrics` on the gateway from the same run: `nia_gateway_requests_total{outcome="allowed"} 7`, `nia_gateway_requests_total{outcome="denied_tool"} 1`, `nia_monitoring_actions_total{action="flag"} 1`, `nia_monitoring_actions_total{action="revoke"} 2`, `nia_monitoring_actions_total{action="kill"} 1`, the same eight-call sequence, one more way to see it.

One honest gap this specific run surfaced and is worth stating plainly rather than glossing over: `niactl agent inspect -ref agent:invoice-agent`, read right after the kill, still shows the agent's `state` as `active`. The kill above went through `internal/monitoring.Monitor` calling `internal/policy.Kill` directly, inside `cmd/gateway`, which is correct, that's what actually revokes access, but it never touches `cmd/api`'s own `AgentRegistry`, only a manual `niactl kill` (which goes through `cmd/api`'s `handleKill`) calls `SetState` on it. So an automatic, risk-triggered kill is fully enforced, `policy.Check` genuinely denies the next call, the way step 8 above proves, but the control plane's own inventory doesn't yet reflect it, `GET /agents/{ref}` can report an agent as active that is, in every way that matters to the gateway, already killed. That's a real, previously undiscovered gap, not a hypothetical one, found by actually running this scenario end to end with a real Tessera backend rather than assuming the two in-memory registries stayed in sync. It's not fixed in this pass, closing it means `internal/monitoring` (running inside `cmd/gateway`) reaching back into `cmd/api` over HTTP on every automatic kill, the same kind of cross-process dependency `internal/incident`'s own doc comment already declines to add for a blast-radius snapshot, and deserves the same deliberate treatment, not a rushed fix bolted onto this README pass.

Reproducing this: bring up `nia-api` and `nia-gateway` both pointed at the same Tessera instance (`NIA_TESSERA_BASE_URL` and the signing key, see "Running locally" below), start the gateway with `NIA_RISK_FLAG_AT=4 NIA_RISK_REVOKE_AT=8 NIA_RISK_KILL_AT=15` and `NIA_TOOLS_API_URL` pointed at `nia-api` (so the `risk_class` signal is scored, not just `novel_tool`), then `niactl simulate attack -scenario agent-hijack`. Lower or higher thresholds change exactly where flag/revoke/kill fire, the point isn't the specific numbers, it's that they're real thresholds being crossed by a real accumulating total, not a scripted outcome.

## Status

Package boundaries, interfaces, and in-memory reference implementations exist for every one of the seventeen MVP components. `internal/policy` additionally has a second, real implementation, `TesseraHTTPClient`, that drives an actual Tessera.Service instance over HTTP instead of the in-memory reference. `cmd/api` and `cmd/gateway` pick between the two at startup based on environment (`policy.FromEnv`, unset `NIA_TESSERA_BASE_URL` means the in-memory one, same "runs out of the box" default as before).

What's actually been verified, and how:

- `internal/policy`: unit tests against a fake HTTP server (network failures, malformed and oversized responses, cancellation, concurrent writers) plus a live test that spawns a real `Tessera.Service` process and drives it over actual HTTP (`internal/policy/tessera_client_live_test.go`, opt-in via `NIA_TESSERA_REPO_PATH`, a checked-out Tessera repo with `src/Tessera.Service` already built).
- `cmd/api` and `cmd/gateway` against that same real `Tessera.Service` process, driven over real HTTP end to end, not just through Go's own test harness: registered an agent, killed it through `POST /policy/kill`, and confirmed Tessera's own state showed the kill. This is what caught a real bug (an agent ref containing `:`, NIA's own convention, `agent:billing-reconciler`, fails Tessera's `client_ref` validation outright) that no unit test had a reason to exercise, since none of them used a ref in that shape. Fixed with a reversible encoding at the `TesseraHTTPClient` boundary, see its doc comment, point 5.

- `deployments/docker-compose.yml`, on a real Docker daemon: all five containers (`nia-api`, `nia-gateway`, `tessera`, `openfga`, `postgres`) built and came up healthy, then a client was onboarded through Tessera's real HTTP surface, checked as allowed directly against OpenFGA, killed, and checked again as denied, actual tuples written to and deleted from a real OpenFGA store, not the in-memory one. `deployments/bootstrap-openfga.sh` creates the store and loads the authorization model this needs, see the comment at the top of `docker-compose.yml`. This run caught two more real bugs in Tessera's OpenFGA adapter, both fixed: `IAuthorizationStore` wasn't resolving through dependency injection when pointed at a real store, and `ReadTuplesForClientAsync` filtered OpenFGA's read endpoint by user alone, which OpenFGA rejects outright. Neither the harness tests nor the earlier live test against Tessera's in-memory store had a reason to catch either, only a real OpenFGA instance exercises that code path. See Tessera's own commit history on `feature/openfga-http-adapter` for both fixes.

What has not: `Dockerfile.api` and `Dockerfile.gateway` build correctly for `linux/arm64` and standard `linux/amd64` hosts, unconfirmed on anything more exotic. Multi-replica behavior (more than one `nia-api` or `tessera` instance against the same store) hasn't been exercised, the read-modify-write races that implies are a documented, open gap, see `internal/policy/tessera_client.go`'s doc comment.

- `internal/audit`: the gateway now writes every decision it makes (`gateway.allowed`, `gateway.denied`, `gateway.check_error`) to the audit trail, not just `cmd/api`'s own registration and kill events, closing a gap where the package's own doc comment promised "aggregates events from the gateway" and nothing in the gateway actually did that. `cmd/api` exposes it over HTTP (`GET /audit`, `GET /agents/{ref}/audit`) and `niactl audit` wraps both. Verified with `go test ./... -race` (unit tests for `InMemorySink`'s ordering and eviction, and for both HTTP handlers, including that an unresolved caller correctly produces no event, there's no subject to attach one to) and with a live run: real `nia-api` and `nia-gateway` binaries, driven over actual HTTP by `niactl` and `curl`, registering an agent, calling the gateway both with and without a valid identity header, killing the agent, and reading the result back through `niactl audit -ref`. That live run also confirmed a real limitation head on rather than just asserting it, which is what motivated the next item below: `nia-api` and `nia-gateway` each held their own in-memory sink, so a gateway decision was invisible to `niactl audit`, which only talks to `cmd/api`.

- `internal/audit.PostgresSink`: a real, shared `Store` backing the trail, `database/sql` plus `lib/pq`, schema created on first connect (`CREATE TABLE IF NOT EXISTS`, see `postgres_sink.go`, this table's shape has never changed and doesn't warrant a migration framework yet). `audit.FromEnv` picks it over `InMemorySink` when `NIA_AUDIT_DATABASE_URL` is set, same pattern as `policy.FromEnv`, and `deployments/docker-compose.yml` points both NIA services at the stack's own `postgres` service so they share one trail instead of two. Written somewhere with no network path to the Go module proxy, so it went through three separate confirmations once real internet was available rather than one: `go mod tidy && go build ./... && go vet ./... && go test ./... -race` (clean, including the new code's first real compile), the opt-in live test against a standalone `postgres` container (`NIA_AUDIT_TEST_DATABASE_URL=... go test ./internal/audit/... -run TestPostgresSink_Live -v`, confirms inserts and both read paths against a real database), and the full `docker compose up -d --build` stack, registered an agent through `nia-api`, called `nia-gateway` with no grants yet (denied), killed the agent, then read `GET /agents/{ref}/audit` back from `nia-api` and got `agent.registered`, `gateway.denied`, `agent.killed`, all three, correctly ordered, one process reading back what another process wrote. That last part is the actual point: the two services now genuinely share one audit trail instead of each keeping its own.

- `internal/credentials`: the package already had a full in-memory `Store`, issue, get, list, revoke, but nothing outside the package called it. `cmd/api` exposes it now, `POST /agents/{ref}/credentials` to issue, `GET` to list, `POST /credentials/{id}/revoke` to retire one, and `niactl credential issue` / `list` / `revoke` wrap all three. Issuing requires the agent to already be registered, revoking writes `credential.revoked` to the audit trail the same way every other control-plane action does, so `niactl audit -ref` now shows a credential's whole lifecycle next to registration and kills. Verified with `go test ./... -race`, seven new tests on the in-memory store and six on the HTTP handlers. `cmd/api` has no network path to the Go module proxy in the environment this was written in either, same constraint `PostgresSink` hit, so the whole module was verified once against a local stub of the `lib/pq` import path (nothing committed, no network involved) to get a real build/vet/test pass rather than a hand review of the new code.

- `internal/registry/tools`: same gap, same fix. `cmd/api` now exposes the catalog, `POST /tools` to register, `GET /tools` and `GET /tools/{name}` to read it back, `niactl tool register` / `list` / `get` on top. Registering defaults `risk_class` to `read_only` rather than requiring it, and rejects anything else that isn't `read_only`, `write`, or `destructive`. Verified with `go test ./... -race`, six new tests on the HTTP handlers, same build-verification path as the credentials work above.

- Closing the gap the item above left open on purpose: the gateway now actually consults the tool catalog. Set `NIA_TOOLS_API_URL` (`cmd/api`'s own address) and `handleToolCall` looks the tool up over HTTP, `tools.HTTPReader`, before ever reaching the policy check, 404s outright if nobody registered it, and writes `gateway.unknown_tool` to the audit trail. Unset, this step is skipped entirely, the gateway's original tool-name-only behavior is unchanged, additive rather than a stricter default nothing opted into. The lookup goes back to `cmd/api` over HTTP rather than a second shared store, the same tradeoff the audit trail made before `PostgresSink`, except here a tool's existence changes rarely enough relative to the hot path's actual bottleneck (the policy check) that this is the whole answer, not a stopgap. A lookup error (not "unregistered", "couldn't ask") is treated the same way a failed policy check already was: audited separately, 500, not let through. Verified with `go test ./... -race`, four new tests on `HTTPReader` against a real `httptest.Server`, three on `FromEnvReader`, and three more on the gateway's handler (unknown tool short-circuits before `Check` is ever called, a registered tool proceeds normally, a lookup error is audited and blocked), same build-verification path as everything else in this section.

- `internal/graph` moved past its own stub too. `cmd/api` exposes it now, `POST /graph/nodes` and `POST /graph/edges` to build the graph up by hand, `GET /graph/{id}/neighbors?kind=` for one hop, `GET /graph/{id}/reachable?kinds=` for the transitive blast-radius query the package's own doc comment promises, `-kinds` omitted means every edge kind, the question is usually "everything reachable, however," not one relation type at a time. `niactl graph add-node` / `add-edge` / `neighbors` / `reachable` wrap all four. This is still bookkeeping the graph itself can answer questions about, not enforcement: a `trusts` or `delegates_to` edge doesn't change what `internal/policy`'s live check allows, nothing wires the graph into that path yet, see docs/ARCHITECTURE.md's Delegation row for the honest statement of that gap. Verified with `go test ./... -race`, nine new tests on the HTTP handlers including the same delegation-chain blast-radius scenario `internal/graph/graph_test.go` already covers directly against `InMemoryGraph`, run here over the HTTP layer instead, same build-verification path as everything else in this section.

- `internal/risk` and `internal/monitoring` moved past their own stubs. `risk.HistoryScorer` is the first real `Scorer`, two signals computed without any external dependency: `novel_tool` (has this agent ever called this exact tool before, tracked in process memory) and, when the tool catalog is configured, `risk_class` (weighted by how destructive the tool is, sharing the same `tools.Reader` the gateway's catalog check already uses). `internal/monitoring.Monitor` had a real bug fixed along the way: `ActionRevoke`'s own doc comment promised "one credential revoked" and the code never revoked anything, it just wrote an audit event. It now actually revokes, every active credential belonging to the agent via `credentials.Store` (not a single key, there's no per-call credential attribution in this scaffold to revoke just one, see the doc comment on `revokeCredentials`), and reports plainly in the audit detail when no store is configured rather than silently pretending. Wired into `cmd/gateway`: set any of `NIA_RISK_FLAG_AT`, `NIA_RISK_REVOKE_AT`, or `NIA_RISK_KILL_AT` and every allowed call gets scored and observed, unset (the default) skips monitoring entirely, same additive posture as the tool catalog check. `cmd/gateway` doesn't have a credential store wired into it, so a revoke threshold crossed there degrades to the audited no-op described above rather than a real revoke, that's the next gap, not a hidden one. Verified with `go test ./... -race`: seven tests on `HistoryScorer` including a concurrent-calls race check, ten on `Monitor` (flag, kill, revoke with a store, revoke without one, revoke touching only the calling agent's active credentials) plus four on `ThresholdsFromEnv`, and five more on the gateway's handler (monitoring skipped when unconfigured, a score below every threshold, crossing flag, crossing kill with a real `policy.Kill` call asserted), same build-verification path as everything else in this section.

- `internal/sensitivity` is new: five-level resource classification (`public`/`internal`/`confidential`/`sensitive`/`critical`), rule-based and explainable on purpose, an operator declares "customer.ssn is critical" and a lookup answers it, nothing here infers. It names resources the same way `policy.GrantForData` already does, so a classification and a data grant are meant to line up: an agent authorized to call a tool can still lack the grant for a specific sensitive field the call touches, using the `data` grant kind that already existed in `internal/policy`, not a second authorization system. `FromEnvClassifier` follows the same "unset means off" pattern as everything else, `NIA_SENSITIVITY_RULES_PATH` unset means no rules, every resource classifies as `public`. Verified with `go test ./... -race`, thirteen tests covering rule matching (exact, prefix wildcard, first-match-wins, input isolation from the caller) and `FromEnvClassifier` (unset, a valid rules file, a missing file, malformed JSON, an unknown level, an empty pattern).

- The gateway now actually inspects tool-call arguments instead of only ever seeing a tool name. `POST /tools/{tool}/call` decodes an optional `arguments` object; when `NIA_GATEWAY_RESOURCE_RULES_PATH` is set, a `FieldResourcePolicy` (`cmd/gateway/resources.go`) turns those arguments into resource object names, a `database.query` call with `{"table": "customers", "columns": ["name", "ssn"]}` and a rule naming `table` as the qualifier and `columns` as the fields becomes `customers.name` and `customers.ssn`. Any of those classified `sensitive` or above needs its own `policy.GrantForData` grant, checked and audited the same way the tool-level grant already was, `gateway.denied` naming the specific resource if it's missing, not just the tool. This is the Agent+Tool+Action+Resource decision, not only Agent+Tool: an agent can be authorized to call `database.query` and still not be authorized to retrieve a column an operator flagged as sensitive. `internal/risk.HistoryScorer` picked up a third signal off the same classifier, `sensitive_resource`, weighted higher again when the highest level touched is `critical`. Both new env vars are independently optional, and even with argument inspection on, a resource nobody classified stays `public` and needs no extra grant, so this is additive on top of everything that worked before, not a stricter default nobody opted into. Verified with `go test ./... -race`: eight new tests on `FieldResourcePolicy`, six on its `FromEnv` loader, ten more on the gateway's handler (an empty body still working, a malformed body rejected, arguments ignored when unconfigured, a resource below the sensitive threshold skipping the extra check, a sensitive resource both granted and denied, a data-grant check error audited and blocked), and three new `HistoryScorer` tests for the `sensitive_resource` signal.

- Permissions had a real gap closed: `internal/policy.Client`'s `WriteGrants`/`DeleteGrants`/`ListGrants` have existed since the policy client itself did, but nothing outside the package ever called them, there was no way to actually grant an agent a permission through the running control plane, only through a test constructing an `InMemoryClient` directly. `cmd/api` now exposes `POST`/`DELETE`/`GET /agents/{ref}/grants`, `niactl grant write` / `delete` / `list` wraps all three, and the write path is additive: writing the same grant twice is a no-op the second time, not an error. Verified with `go test ./... -race`, seven new handler tests covering the unregistered-agent case, empty and unknown-kind rejections, the audit event it writes, and that delete only removes what was named.

- Risk scoring moved from judging one call in isolation to a running per-agent total: `internal/monitoring.Monitor` now accumulates every scored call into `cumulative[agentRef]` and compares that total, not the single call's own value, against the flag/revoke/kill thresholds, resetting only on an actual kill, since that's the one action that changes the agent's state enough to justify starting its risk history over. Without this, three separate flags below the kill threshold would never add up to anything, which didn't match how a real escalating compromise looks. `CumulativeRisk(agentRef)` exposes the same number `Observe` itself compares, and `POST /tools/{tool}/call`'s response now carries a `risk` block, this call's own value and signals plus the current cumulative total and whatever action fired, when monitoring is configured, so a caller can see the running total without a separate query. Verified with `go test ./... -race`, five new `Monitor` tests including one that fires fifty concurrent `Observe` calls for the same agent and checks the total lost no updates, plus three new gateway tests asserting the `risk` block's shape and that a kill-triggering call reports `action: "kill"`.

- `niactl simulate attack -scenario agent-hijack` is new: a deterministic attack simulation that drives the real pipeline end to end, agent registration, tool registration, grants, then a scripted sequence of real gateway calls, not printed output standing in for one. The scenario models an invoice-processing agent with broader tool access than its normal work ever uses (a realistic over-privileged setup), escalates through tools it's authorized for but has never called (what `HistoryScorer`'s `novel_tool` and risk-class signals exist to catch), gets a real 403 on a `database.query` call touching `customers.ssn` (deliberately left ungranted at the data level, proving the Agent+Tool+Resource decision from the argument-inspection work above), and, when the gateway is started with risk thresholds set low enough, shows an actual kill mid-sequence: a tool the agent successfully called earlier in the same run gets denied later on, because `policy.Check` now reads the kill sentinel, not because the request changed. See "Attack simulation" in `docs/ARCHITECTURE.md`. Verified with `go test ./... -race`: a scenario well-formedness check (every tool a step or grant names is actually registered), unit tests on the transcript-printing functions, and an integration test that drives `runScenario` against fake `cmd/api` and `cmd/gateway` HTTP servers and asserts on the actual call sequence and containment detection.

- `internal/incident` is new: a structured record for every flag, revoke, or kill `internal/monitoring.Monitor` actually decides on, not just the audit trail's free-text line. Each record carries the agent, the correlator string, the action taken, the risk value and signals that triggered it, and the cumulative total at that moment, one record per containment decision rather than something reconstructed later by grepping audit events for a shared incident string. Records are created inside `internal/monitoring`, which only runs in `cmd/gateway`, so that's also where they're read back from, `GET /incidents` (`?ref=`, `?limit=`) and `GET /incidents/{id}`, not `cmd/api`; `niactl incident list` / `get` talk to the gateway's own address for exactly that reason, same as `gateway call` and `simulate attack` already do. This deliberately doesn't carry a blast-radius snapshot yet, see `docs/ARCHITECTURE.md`'s "Structured incident evidence" section for why, doing that means `internal/monitoring` reaching back into `cmd/api` over HTTP mid-decision, a dependency this pass didn't add to the containment path itself. Verified with `go test ./... -race`: seven tests on `InMemoryStore` (assignment, lookup, per-agent filtering, limit, empty store), and new `internal/monitoring` and `cmd/gateway` tests covering record creation on flag/kill, the cumulative value at the moment of a kill, an incident-store failure not blocking the containment decision itself, and the gateway's `GET /incidents` / `GET /incidents/{id}` handlers both configured and not.

- The identity graph stopped being something an operator had to build by hand before it could answer anything. Agent registration, tool registration, credential issuance, and grant writes now all add their own nodes and edges to the graph as they happen, `handleRegisterAgent` adds the `Agent` node, `handleRegisterTool` adds the `Tool` node, `handleIssueCredential` adds a `Credential` node and a `bound_to` edge to the agent it was issued for, `handleWriteGrants` adds a `grants` edge (and the object's node, if nothing had registered it yet) for tool and data grants, `api_group`/`endpoint` grants skipped since neither has a natural graph node on either side. All of it is fail-open the same way audit writes are: the registration or grant that actually mattered already succeeded, a graph write failing alongside it is logged, not turned into a failed response. A pre-existing inconsistency got closed along the way too, `EdgeBoundTo`'s own doc comment already said "Credential -> Agent" but no `NodeCredential` kind existed anywhere, added now, closing that gap for real rather than leaving the comment aspirational. One gap is left open on purpose: `internal/graph.Graph` has no edge-removal method, so deleting a grant does not remove the matching `grants` edge, the graph is a superset of what's currently granted after a revoke, not a stale-safe mirror, `internal/policy.ListGrants` stays the source of truth for that. `GET /graph/{id}/blast-radius` (`niactl graph blast-radius`) turns a `Reachable` traversal into what an incident review actually wants first: total reachable nodes, a count by kind, which reachable data resources classify `sensitive` or `critical` through `internal/sensitivity`, and a `HIGH`/`MEDIUM`/`LOW` severity call, a fixed, explainable rule (critical resource or five-plus reachable agents/tools is `HIGH`, a sensitive resource or one-plus reachable agent/tool is `MEDIUM`, otherwise `LOW`), not a tuned score. `niactl simulate attack` now ends by printing the scenario agent's own blast radius, reading back what its own grant writes auto-populated, proof this isn't hand-built for the demo. Verified with `go test ./... -race`: two new tests on `graph.Summarize`, twelve new `cmd/api` tests (auto-population from registration, tool registration, credential issuance, and grants, `api_group`/`endpoint` grants correctly adding no edge, `blast-radius` on an empty graph, counting by kind, an unknown edge kind, and all three severity tiers using a fake `sensitivity.Classifier`), and two new `cmd/niactl` tests on `printScenarioBlastRadius` (a real total/severity/critical-resource response, and an unreachable API reported honestly rather than panicking).

- Phase 10: `cmd/api` itself had no authentication at all, every `operator`/`revoked_by`/`disabled_by`/`enabled_by`/`rotated_by` field across every handler was whatever the caller typed into the request body, written straight into the audit trail unverified. - Phase 11: real downstream tool forwarding. Before this, `handleToolCall` proved a decision and stopped, its own doc comment said as much: "a real deployment forwards the request to the tool's actual transport here." - Phase 12: tamper-evident audit. Before this, `internal/audit` recorded events durably but nothing stopped a row from being edited or deleted after the fact and having that go unnoticed, an operator with database access (or a bug, or a bad migration) could rewrite history and there was no way to tell. New `internal/audit/chain.go`: every event gets a SHA-256 hash computed over a deterministic canonical encoding of its own fields plus the previous event's hash, `event_n.hash = SHA256(canonical(event_n.data) + event_(n-1).hash)`, so each event is cryptographically bound to everything before it, the first event in a store chains from a fixed genesis hash (64 zero characters). `Verify` recomputes every hash independently from the stored data, it never trusts a hash the writer claims, and reports exactly what broke: a modified event fails its own hash check, a deleted or reordered event breaks the previous-hash link to its neighbor, an inserted event either breaks that link or fails its own hash depending on where it lands. Both storage backends implement `audit.Chained`. `InMemorySink` tracks the running chain in memory and honestly reports `StartsAtGenesis: false` once its bounded buffer has ever evicted an old event, so routine memory limits are never mistaken for a broken chain. `PostgresSink` adds `hash`/`prev_hash` columns via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, so existing deployments upgrade without a destructive migration, old pre-chain rows keep an empty hash and are skipped by verification rather than flagged broken; a new singleton `audit_chain_state` row tracks the last hash and `Append` takes it with `SELECT ... FOR UPDATE` inside a transaction, so concurrent appends from `cmd/api` and `cmd/gateway` writing to the same audit database can't race and produce two events claiming the same previous hash. Verification is exposed both ways: `GET /audit/verify` on the control plane, `niactl audit verify` on the CLI, both fail closed with 501 if the configured audit backend doesn't implement `audit.Chained` rather than silently reporting success. Found and fixed one real bug during verification, not by inspection: hashing at write time used Go's full nanosecond-precision timestamp, but Postgres's `TIMESTAMPTZ` rounds to microsecond precision on insert, so every event read back from a real database recomputed to a different hash than the one stored, every single row falsely reported as modified. Confirmed the rounding behavior directly against Postgres, fixed by truncating the timestamp to microseconds before hashing and before inserting, so the hashed value and the stored value can never disagree. Verified with `go test ./... -race`: `internal/audit/chain_test.go` covers modification, deletion, insertion, and reordering against an in-memory fake store, plus the genesis and skip-on-truncation cases; `cmd/api/audit_test.go` adds three tests against the HTTP endpoint including one that tampers a real `InMemorySink`'s reported chain and confirms the break surfaces over `GET /audit/verify`. Separately, five live tests in `internal/audit/postgres_sink_live_test.go` run the same four tampering cases with real SQL against a real Postgres database, each doing the actual thing an attacker with row-level database access would have to do, an `UPDATE` for modification, a `DELETE` for deletion, a `DELETE` followed by an `INSERT` reusing the freed id for insertion (a plain `INSERT` can't land a row between two contiguous serial ids), and a swap of two rows' varying fields for reordering. Also run as a full live stack outside the test suite: real `nia-api`, `nia-gateway`, and `Tessera.Service` sharing one Postgres database, a five-event chain written across both processes, `niactl audit verify` reporting clean, then a direct SQL `UPDATE` on one gateway-written row, and `niactl audit verify` catching it, naming the exact sequence number and the reason. What this doesn't close, stated in `internal/audit/chain.go`'s own doc comment and repeated in `docs/SECURITY_INVARIANTS.md`: hash chaining provides tamper evidence, it does not by itself prevent a privileged database administrator from rewriting both the events and the chain, closing that gap needs external or WORM storage, or periodically signed checkpoints published somewhere the database itself can't reach, neither of which exists yet, though the `audit.Chained` interface was shaped so either can be added without redesigning the audit API. Verification is also on demand, not continuous, nothing here polls `Verify` automatically or alerts on a break, an operator or a monitoring job has to call it. See `docs/ARCHITECTURE.md`'s new "Tamper-evident audit" section, `docs/SECURITY_INVARIANTS.md`'s invariant 15, and the rewritten threat 9 in `docs/THREAT_MODEL.md`.

- Phase 13: distributed state, a security review of every state store rather than a new feature. The question the directive asked was specific: can two gateway processes disagree about whether an agent should be denied. Kill state, credential state, and policy/grants state were already safe, all three already routed through `policy.Client`/`credentials.Store` backends with a real shared implementation behind an env var. Risk enforcement state was not: `internal/monitoring.Monitor` kept its running per-agent risk total in a bare `map[string]float64`, private to whichever `cmd/gateway` process built it, which meant an attacker (or just load-balanced traffic) spreading tool calls across replicas kept any single replica's own view of an agent's risk under the kill threshold indefinitely while the agent's real aggregate behavior kept climbing, no replica ever saw the whole picture. New `internal/monitoring.RiskStore` interface, `Accumulate`/`Get`/`Reset`/`TrackedAgents`, with `InMemoryRiskStore` (the old behavior, now named and isolated) and `PostgresRiskStore` (`NIA_RISK_DATABASE_URL`, same opt-in `FromEnv` convention as credentials and audit), `Accumulate` a single UPSERT so Postgres's own row locking serializes concurrent writers, no read-then-write window. `Monitor`'s public API is unchanged, `NewMonitor` still builds the old in-memory behavior by default, `NewMonitorWithRiskStore` is what `cmd/gateway`'s `main()` now actually calls. Verified with `go test ./... -race` at three levels: unit tests on both `RiskStore` implementations, `cmd/gateway/distributed_test.go` building two independent `*gateway` values sharing only the store, proving a kill triggered through one instance is enforced by the other which never called `Kill` itself, and a live test opening two independent `*PostgresRiskStore` connection pools and racing 100 concurrent updates through a real database. Also run as a genuine live stack outside the test suite, not simulated: two real `nia-gateway` processes on different ports, one real `Tessera.Service`, one real Postgres database, risk-generating calls split across both processes, a kill crossing threshold on the second process, and the first process, which never called `Kill` itself, denying the agent's next request with a real 401. That live run surfaced one real, narrow bug this pass did not introduce and did not fix: `CREATE TABLE IF NOT EXISTS`, the schema-creation pattern every `PostgresX` constructor in this codebase uses, is not itself safe against two brand-new processes racing to create the same table for the first time against a fresh database (`pq: duplicate key value violates unique constraint "pg_type_typname_nsp_index"`), transient and harmless once the race resolves, but real, named here and in `docs/ARCHITECTURE.md` rather than quietly worked around. What's still process-local, stated plainly rather than implied fixed: `internal/incident`'s structured records and `internal/registry.InMemoryAgentRegistry`'s cached metadata, neither gates an authorization decision, and the identity graph, addressed on its own terms in phase 16 below. See `docs/ARCHITECTURE.md`'s new "Distributed state" section, `docs/SECURITY_INVARIANTS.md`'s invariant 16, and the rewritten threat 11 in `docs/THREAT_MODEL.md`.

- Phase 14: credential lifecycle and replay, a focused review of issue, verify, revoke, expire, disable, rotate, and what a captured credential can still do. Found one real, live exposure, not by inspection alone, by actually reading a real `niactl credential issue` response: `credentials.Credential.SecretHash`, the stored digest, had no `json` tag at all and was serialized into every response returning a `Credential`, issue, rotate, list, the same class of leak the directive named directly ("credential hashes/digests must not be exposed through APIs or logs"), even though a SHA-256 digest isn't reversible to the secret it was computed from. Fixed with a single `json:"-"` tag, confirmed against a real running `nia-api` before and after, the field was there, then it wasn't. The rest of the lifecycle was already sound at the store level, this pass added gateway-level tests, not store-level ones, because a wiring mistake in how `cmd/gateway` builds its resolver is a different failure mode a store test can't catch: rotation replay (the old secret rejected, the new one accepted, once `Rotate` has returned), expiry, disable, and, closing the gap the security invariant already claimed but a header-spoofing test hadn't directly proven, that a valid credential for one agent plus a forged `X-Agent-Ref` for another still authorizes against the credential's real agent, not the header. Bearer credential replay itself, presenting a still-valid captured secret a second time, was reviewed and found genuinely unhandled, not a gap this pass closed: `<id>.<secret>` is a bearer token, not a nonce or challenge/response, there is no per-request freshness check anywhere in this path, and closing it is a real protocol change (a nonce-based scheme), not something fixable inside `internal/credentials` as it exists. Documented as a stated, permanent limitation rather than left implicit. Verified with `go test ./... -race`: new tests in `internal/credentials/credentials_test.go` and `cmd/api/credentials_test.go` confirming `SecretHash` never appears in JSON by name or value, and four new `cmd/gateway/authn_test.go` tests for rotation replay, expiry, disable, and the `X-Agent-Ref` override attempt, all exercised through the real `handleToolCall` path. See the extended threat 1 in `docs/THREAT_MODEL.md` for the replay statement and `docs/SECURITY_INVARIANTS.md`'s invariant 17.

- Phase 15: concurrency and race security tests, making the directive's own list of scenarios (request vs kill, kill vs request, request vs revoke, revoke vs request, credential rotation vs request, credential rotation vs replay, restore vs previously revoked credential) into actual tests rather than trusting `go test -race`'s data-race detection alone to stand in for the correctness property that actually matters. A data race and a correctness bug are different things, code can be perfectly race-free under `-race` and still let a request slip through that started concurrently with a kill; the property this phase tests for is that once a state-changing call (`Kill`, `Revoke`, `Rotate`) has actually returned, no request that raced it can still succeed, not that every racing request lands on a particular side of it, a request genuinely concurrent with the change may reasonably go either way. New `cmd/gateway/concurrency_test.go`: fifty goroutines firing `handleToolCall` requests gated on a shared start signal, racing a real `policy.Kill`, `credentials.Store.Revoke`, or `credentials.Store.Rotate` call, `wg.Wait()`, then one final request after everything has settled, asserted denied (or, for rotation, the new credential asserted allowed and the old one denied). Collapses the directive's seven named scenarios into three concurrent tests (kill, revoke, rotation covering both "vs request" and "vs replay" for rotation) plus one deliberately sequential test, restore vs a previously revoked credential, because that scenario is about state-transition ordering, not timing, a kill cascades into revoking the agent's credentials, `Restore` only clears the kill sentinel, and this test confirms `Restore` does not quietly resurrect a credential the kill had already revoked. All five pass individually and repeated five times under `go test -race`. See `docs/SECURITY_INVARIANTS.md`'s invariants 1 and 11, extended in this pass to cite these tests directly, and the extended threat 8 in `docs/THREAT_MODEL.md`.

- Phase 16: identity graph lifecycle semantics, resolving an ambiguity the graph already lived with rather than adding anything new. `internal/graph.Graph` has no edge-removal method, `handleDeleteGrants` never touches the graph, so a `grants` edge outlives the grant it recorded once that grant is deleted, this was already true and already informally noted in `niactl`'s usage text as a "known gap." The directive asked for a choice, not a fix: either make the graph a live mirror (add edge removal, keep every writer in sync with everything that can end a relationship, a grant deletion, a credential revocation, a kill) or formalize it as historical and append-only, a superset of current authorization rather than an exact copy. This pass chooses the second, explicitly, in code and in docs rather than leaving it an implied-temporary gap: an incident review asking "what has this agent ever had access to" is a real, different question from "what does it have access to right now," and losing the first answer the moment a grant is revoked would work against exactly the kind of post-incident use this graph exists for. `internal/policy.Check`/`ListGrants` remains the only source of truth for current authorization, always, restated directly in `internal/graph`'s own package doc comment, `cmd/api/main.go`'s `handleGraphReachable`/`handleBlastRadius`/`graphAddGrantEdges` doc comments, `docs/ARCHITECTURE.md`, `docs/DATA_MODEL.md`, and `niactl`'s usage text, so a reader encountering any one of them gets the same answer. New test, `cmd/api/graph_test.go`'s `TestGraphEdgeSurvivesGrantDeletion_ButPolicyCheckReflectsCurrentTruth`, writes a grant, confirms `policy.Check` allows it, deletes it, confirms `policy.Check` now denies it, and confirms the graph's `grants` edge is still there, both halves in one test so neither claim is checked in isolation. Verified live too, against a real running `nia-api` with a real Tessera backend: wrote a tool grant, confirmed it in `graph neighbors`, deleted it, confirmed `grant list` came back empty while `graph neighbors` still showed the edge, exactly the behavior now documented rather than assumed. See `docs/SECURITY_INVARIANTS.md`'s new invariant 18, `docs/ARCHITECTURE.md`'s "The identity graph" section, and `docs/DATA_MODEL.md`.

- Phase 17: authentication by default, and two verification holes. The one worth stating first, because it was live and shipped: `cmd/api` accepted every request unauthenticated unless `NIA_OPERATOR_TOKENS_PATH` was set, and `deployments/docker-compose.yml` never set it, so the reference stack exposed agent registration, grant writes, credential issuance, kill, restore, and the whole audit trail on port 8080 to anyone who could reach it. `cmd/gateway` had the same shape on its three operator-facing read endpoints (`/incidents`, `/incidents/{id}`, `/risk/{ref}`) while the tool-call path beside them demanded a verified credential. Both closed by inverting the default rather than by setting a variable in one compose file: `opauth.FromEnvEnforced` makes an unset tokens path a startup failure for both binaries, with `NIA_ALLOW_UNAUTHENTICATED=1` as the one deliberate, logged escape hatch. Alongside it, `internal/audit.Verify` used to return `OK` on a tampered chain two ways, a blanked `hash` column was skipped as "predates chaining" and a truncated chain left everything that remained perfectly self-consistent; a blank hash following a hashed one is a break now, and `Chain.Tip` compares the last event against the chain head recorded in a separate table. `credentials.Verify` returned early on an unknown id, making it measurably faster to reject than a real id with a wrong secret, which is an oracle for which credential ids exist, so both store implementations now do the same work either way. And CI ran no Postgres-backed tests at all, every live test skipping for want of a DSN, so a green badge covered gofmt, build, vet and the in-memory implementations only. Verified with the audit, credentials and monitoring live tests against a real Postgres 16 container, repeated three times against the same long-lived database to prove the suite cleans up after itself, and with both binaries driven by `curl`: `nia-api` refusing to start with no tokens path, then 401 on `/agents`, `/policy/kill` and `/audit` without a token and 200 with one, `nia-gateway` 401 on `/incidents` and `/risk/{ref}`, and an uncredentialed tool call still failing with its own credential error rather than the operator one.

- Phase 18: a hot-path authorization check that reads live OpenFGA, and a defect that had been invisible the whole time. `TesseraHTTPClient.Check` answers from Tessera's declared grant list, because Tessera's HTTP surface exposes nothing else, and that diverges from live state in the fail-open direction: a kill deletes an agent's tuples but leaves its declared grants, restore clears the sentinel without rewriting them, so between a restore and the next write the declared list says "granted" for something no tuple backs and the gateway allows the call. `internal/policy.OpenFGAChecker` asks the authorization store itself, with writes, `ListGrants` and `IsKilled` still going through Tessera so it remains the single writer. Running that against the real pair immediately turned up the larger problem: NIA encoded tool and data grants as `api_group` values prefixed `tool:` and `data:`, which Tessera's `GrantTupleMapper` turns into the OpenFGA object `api_group:tool:<name>`, and OpenFGA rejects an object whose id half contains a colon. No NIA tool or data grant could be written to a real OpenFGA-backed Tessera at all, onboard returned a 500 and nothing was stored. Nothing caught it because every test in `internal/policy` ran against a fake server that accepted any string, and the earlier live stack run only ever onboarded plain `api_group` grants. The prefixes are `tool/` and `data/` now, with no migration needed, because no tuple in the old shape was ever successfully stored. Verified against a real Tessera.Service container talking to a real OpenFGA: the encoding defect reproduced first, with Tessera's own log showing OpenFGA's "invalid 'object' field format", and passed after the change, and the fail-open reproduced in the same run with the declared list answering `allowed=true` and live OpenFGA `allowed=false` for the same grant. What this did not do is make the model more expressive: tools and data still reach OpenFGA as `api_group` objects with prefixed names, flat membership, no type of their own and no hierarchy, because real types mean changing Tessera's `Grant` model, its mapper and `deployments/openfga-model.json` together.

- Phase 19: volume and ordering detection, and a behavioural baseline that replicas share. Every signal before this judged one call on its own, so the whole category `docs/THREAT_MODEL.md`'s threat 10 describes was invisible: a compromised agent working through tools it was already allowed to call, at whatever speed it liked, scored zero. `call_rate` fires when an agent's calls inside a configured window cross a configured threshold, with a flat weight per call over the line rather than one that scales, because the score feeds a cumulative total that can kill an agent and a scaling term compounds into a kill nobody can explain afterwards. `novel_transition` fires when an agent goes from one tool straight to another in an order it has never used, which catches what rate misses, familiar tools at ordinary speed in an unfamiliar sequence; a repeat of the same tool deliberately does not count, since that is the most ordinary thing an agent does and counting it would fire on essentially every agent's second call. Both are off unless configured, because a threshold nobody picked for their own traffic either never fires or fires on everything. The history behind them moved into `risk.CallHistory`, and `NIA_RISK_HISTORY_DATABASE_URL` makes it shared, which closes the other half of phase 13's work: that pass shared the cumulative risk total, this one shares the signals the total is built from, so the same tool no longer scores `novel_tool` once per replica and again after every restart. Verified end to end against the whole stack: six calls with the threshold at 3 per 60s scored `novel_tool` on the first, nothing on the second and third and `call_rate` on the fourth through sixth, then a call to a second tool fired `novel_tool`, `novel_transition` and `call_rate` together to cross the kill threshold, after which `GET /agents/{ref}` reported `effective_state=killed` from the live sentinel and the next call with a valid credential got a 401 because the kill had cascaded into revoking it.

- Phase 20: two defects found by rechecking phase 17 to 19 rather than by planning them, which is the reason the recheck happened at all. The chain tip added in phase 17 compared the last event's hash against a value read in a second, separate query, so an append landing between the two reads made `GET /audit/verify` report a truncation on a healthy trail. For a verifier that is the worst kind of bug, the first false alarm is what teaches an operator to stop believing the real one, and `cmd/api` serves verification while `cmd/gateway` is appending, so it was the ordinary case rather than a rare one; `Chain` reads both under one `REPEATABLE READ` snapshot now, and the test for it was confirmed to fail without the fix before being kept. And none of the four `PostgresX` constructors bounded its connection pool, which went unnoticed while there were three of them and one process: running the live suite with both binaries up produced `pq: sorry, too many clients already` and a lost update in a test that had passed minutes earlier with nothing else connected. Eight open, four idle, a thirty-minute lifetime, in all four. The live suite now passes three consecutive runs with both binaries connected to the same database, where it failed every run before.

- Phase 21: rate limiting, body caps and connection deadlines, the prevention half of what phase 19 only detected. Detection scores a burst and feeds containment; nothing in the request path said no. `internal/ratelimit` is a token bucket used twice on different keys: keyed by client address it wraps both binaries' whole mux in front of authentication, which is the case that matters most because an uncredentialed flood costs a credential or token lookup per request and is never audited, there being no resolved identity to attribute an event to; keyed by agent ref it runs inside `handleToolCall` immediately after identity resolution, before the body is decoded and well before the catalog lookup, policy check, scoring and forwarding. The two are not redundant, one agent can call from many addresses and one address can present many agents' credentials. Both default to on, unlike every other `FromEnv` here, because a limiter that only protects deployments whose operator remembered a variable protects almost nobody, and that is the exact shape of the bug phase 17 started from. `X-Forwarded-For` is ignored unless explicitly trusted, since on a directly reachable process trusting it lets anyone mint unlimited buckets by varying a header, and the key table is bounded and evicts idle buckets first, an unbounded map keyed by attacker-chosen input being itself the denial of service this prevents. Alongside it, fourteen handlers called `json.NewDecoder(r.Body).Decode` with nothing bounding it, so an unauthenticated POST with an endless body was read until the process ran out of memory, and only `ReadHeaderTimeout` was set on either server, which bounds the headers and nothing else. One middleware caps every body at 1 MiB, and `ReadTimeout`, `WriteTimeout`, `IdleTimeout` and `MaxHeaderBytes` are all set, with the gateway's write deadline deliberately longer than its own downstream client timeout so a slow tool does not become a broken one. Verified against both binaries: `nia-api` at 2/s burst 3 answered 200 200 200 then 429s with `Retry-After`, kept serving `/healthz` throughout, refused a 2 MiB body while a normal one returned 201, and counted the refusals on `/metrics`; `nia-gateway` with a per-agent limit let one agent through twice then refused it four times while a second agent from the same address was unaffected.

- Phase 22: the last two stores that kept state in a process-local map. An incident record is the evidence for why NIA killed or revoked an agent, the risk value, the signals and the cumulative total that triggered it, and it lived in a map that died with the process, so a restart left only the audit line saying containment happened with none of the reasoning behind it, and across replicas `GET /incidents` answered from whichever gateway took the request. `internal/incident.PostgresStore` fixes that, with signals stored as JSONB in the same row rather than a child table, because the record is evidence and evidence is easier to trust when one row is the whole thing. `internal/registry.PostgresAgentRegistry` is narrower, no authorization decision reads the registry and `GET /agents/{ref}` checks kill state live against the policy client, but an inventory that disagrees with itself is not a property a control plane gets to have: a second `cmd/api` replica returned 404 for an agent the first had registered. `Register` relies on the primary key rather than a read-then-write, because across replicas that leaves a window where both see "not registered" and both insert. Verified against a real Postgres and then through the binaries, which is the part that matters for a durability claim: an agent registered through one `nia-api` was still listed after the process was killed and restarted and visible from a second replica on another port, and a containment decision recorded by one `nia-gateway` came back with its full signal breakdown after that gateway was killed and restarted, and from a second replica that had never handled the call.

- Phase 23: roles for operator tokens, so authentication stopped being the whole story. Phase 17 gave `cmd/api` a verified caller identity and nothing more, which left the gap `docs/SECURITY_INVARIANTS.md` named directly, an authenticated operator who should not be able to kill agents could kill agents. Three permissions and three roles, with the whole mapping in one file: `viewer` reads, `operator` also changes what exists, `admin` also kills and restores. Kill is its own permission rather than part of write because its consequence is immediate and total, it deletes an agent's tuples and cascades into revoking every credential the agent holds, and read is separate from write for the ordinary reason, an on-call engineer investigating an incident needs the audit trail and the incident records without needing the ability to issue credentials while they are in there. Every route declares the permission it needs at the point the route is declared, so the answer to "who can call this" is visible next to it. Roles are required in the token file rather than defaulting, because defaulting to admin would silently keep the gap this closes and defaulting to viewer would silently break a deployment that thought it had granted more, and an unknown role name is a startup error naming the valid ones. 401 and 403 stay distinct, since "I don't know who you are" and "I know exactly who you are and you may not do this" are different facts, and the 403 body names the caller and the roles it holds so someone debugging their own access does not have to guess. Verified against the real binary: a viewer got 200 on `GET /agents` and 403 on `POST /agents`, an operator registered an agent and was refused both kill and restore, an admin performed the kill, an unauthenticated request got 401 rather than 403, and a token file with a missing or misspelled role stopped the process at startup. Still open and stated rather than implied solved: the roles are global rather than scoped per agent or business unit, so an operator who may write grants may write them for any agent. One more was found along the way and deliberately left for its own pass: `GET /agents` returned the registry's cached state with no live kill check, so a killed agent still listed as `active` even though `GET /agents/{ref}` reported it correctly, see phase 26.

- Phase 24: expiry and revocation for operator tokens, which phase 23 explicitly left open. A token entry can carry an `expires_at`, checked at verify time against the clock rather than swept in the background, the same choice `credentials.Credential.Effective` makes and for the same reason, nothing has to be running for an expired token to stop working. The tokens that actually leak are the ones issued for a migration eighteen months ago that nobody revisited, so an expiry that needs no follow-up is most of the value. Revocation is `internal/opauth.ReloadingStore`: the token file is re-read when its modification time or size changes, at most once every two seconds, so removing a line retires that token on every process reading the file with no restart and no coordination between replicas, and a `Verify` on the hot path costs a stat rather than a parse. The half that matters more than the feature is what happens when a reload fails: the previously loaded tokens are kept and the failure logged, because a half-saved file or a stray comma during an edit locking every operator out of the control plane at once is a worse outcome than a retired token surviving a few more seconds. Verified against the real binary, not only the tests: a token with an `expires_at` in 2020 got 401 while a valid one got 200, deleting a third token from the file revoked it within seconds while the valid one kept working, and corrupting the file mid-edit left the valid token working with the parse failure logged. What this deliberately is not is an issuance API, there is no endpoint that mints an operator token, the first one is written into the file by hand as a deployment step, and revocation is eventual within the reload interval rather than instant.

- Phase 25: a shared lock for grant writes, closing a race `internal/policy/tessera_client.go`'s own doc comment had described since it was written and said was not implemented. `WriteGrants` and `DeleteGrants` read the agent's state, merge, then onboard the merged set, because Tessera has no incremental grant endpoint, and the per-agent mutex in that client covers one process. Two `cmd/api` replicas adding a different grant to the same agent at the same moment could leave only one of the two written, with no error on either side, which is the quiet kind of authorization bug: nothing fails, the grant simply is not there. `PostgresLocker` takes a session-scoped advisory lock keyed on the agent ref for the whole read-merge-write, session-scoped rather than transaction-scoped because the critical section is several HTTP calls to Tessera and holding a transaction open across a round trip to a third service ties up a connection for as long as that service is slow. It uses the two-argument advisory lock form under a fixed class id so it cannot collide with the call-history locks `internal/risk` already takes, and sets a `lock_timeout` so one stuck replica cannot block every other replica's grant writes for that agent indefinitely. A failure to take the lock fails the write rather than proceeding, since proceeding would silently be the unserialized behaviour the lock exists to prevent. Verified against a real Postgres, including the test that matters most: two client instances standing in for two replicas writing grants for the same agent, counting how many onboard calls were in flight at once, confirmed to report two without the lock installed and one with it. Scope worth stating, the lock covers grant writes only: `Kill` and `Restore` are not read-modify-write and rely on Tessera's own sentinel-first ordering, so putting them behind a distributed lock would add latency without adding a guarantee.

- Phase 26: the list endpoint reads the live kill sentinel, which the single-agent endpoint has done since phase 13 and this one never did. The registry's `State` field is a cache updated by `handleKill`, `handleRestore` and registration, and it goes stale for exactly the case that matters most, because `cmd/gateway`'s automatic risk-triggered kills go through `internal/policy` from a different process and never touch `cmd/api`'s registry at all. So the same control plane gave two different answers about the same agent depending on which way you asked, and the wrong one was the one an operator scanning a list during an incident would see. Both endpoints return the same `agentReport` shape now, with `effective_state` from the live check and `kill_sentinel_checked` saying whether that check actually answered, and the registry's own cached `State` still on the wire so the two can be told apart. The checks run eight at a time: each is an HTTP round trip to Tessera with a real policy client, so unbounded fan-out over a large inventory would be a self-inflicted load spike against the policy engine and a serial loop would make the endpoint unusably slow for the same inventory. A failed check leaves the cached state showing and says so rather than guessing in either direction. Found by watching a real `niactl list` during phase 20's recheck rather than by reading the handler, which is the second time that pass turned up something inspection had missed. The cost is stated rather than hidden: listing N agents makes N kill-sentinel checks, which is a round trip or two of wall time at the populations this is built for, and a very large inventory would want a bulk sentinel read that `policy.Client` has no method for today.

- Phase 27: two gaps `internal/policy/tessera_client.go`'s own doc comment had listed as unreachable through the `Client` interface, both now reachable. `Restore` takes an operator and signs Tessera's request with it, the same way `Kill` already did: Tessera takes the actor from the token subject and never from the request body, so every restore before this showed up in its audit trail attributed to NIA's configured system identity, which is exactly the wrong answer for the action an incident record most wants tied to a person. A blank operator is refused by both client implementations before any request goes out, and `cmd/api` rejects it with 400 rather than letting the error come back as something about Tessera. And `SetBusinessUnit` exists, which nothing did before: an agent registered with a business unit had it recorded in NIA's own registry and nowhere else, because there was no path through this interface to declare it, so the Tessera side always read empty no matter what was asked for. It is implemented as the same read, merge, write shape `WriteGrants` uses, passing the existing grants straight back through, because Tessera's onboard is a full state reconcile and sending the attribute alone would delete them, and it takes the same locks and refuses a killed agent for the same reasons. Propagation from registration is fail-open, the registration itself has already succeeded and a failure to declare an attribute is logged rather than turned into a failure the caller would reasonably retry. Verified against a real Tessera: the business unit lands on the real record, the agent still has its grant afterwards, and a later grant write leaves the attribute in place. The test asserting that `Restore` signed as the system subject was replaced by one asserting it signs as the operator, which is the clearest way to see that the old behaviour was tested and documented rather than accidental.

- Phase 28: signed checkpoints, the external anchor `internal/audit/chain.go` has named as missing since phase 12. The hash chain catches an attacker who modifies, deletes, inserts or reorders events without recomputing the rest. It cannot catch one who rewrites the events and every hash after them consistently, because the result is a valid chain over the wrong events and verification reports it intact, correctly. A checkpoint is a signed statement that at some moment the tip was a particular hash at a particular sequence number, signed with a key that is deliberately not in the audit database, so rewriting history now also requires forging a signature the rewriter cannot produce. `GET /audit/verify` checks against the latest checkpoint automatically once one exists, and reports the two answers separately, because a chain that broke on its own terms and a chain that is internally perfect but is not the history that was signed are different findings. Taking a checkpoint is an explicit operation (`niactl audit checkpoint`) rather than a schedule, since one written by the same process on the same cadence into the same database as the events it covers is most of the ceremony and little of the guarantee, and `niactl audit checkpoints` exists so an operator can archive them somewhere the database cannot reach. Signing a chain that does not already verify is refused: a signed statement that a broken chain was the tip would later read as proof the damage was legitimate history. Proved end to end against a real Postgres and through the running binary: a row rewritten, its hash recomputed, the following row relinked and `audit_chain_state` updated, after which `niactl audit verify` returned `"OK":true,"Breaks":null` from the chain walk and `"matches_checkpoint":false` from the anchor, naming the rewritten event. What it does not do, stated rather than implied: checkpoints live in the audit database by default, so an attacker with write access there can delete them, they just cannot forge one, which degrades the attack from rewriting history into something that verifies to destroying the anchors, which is noisy and leaves the trail visibly unanchored rather than convincingly wrong.

- Phase 29: the gateway looks at what a response actually contained, not just whether the call was allowed. The request-side check decides what a call is asking for from its arguments, and that leaves a real hole: an agent legitimately granted `database.query` on a table it is entitled to can still receive a column nobody granted, because the downstream decides what goes in the response. Before this the response reached the agent and the only thing recorded was that the call succeeded. `inspectResponseFields` walks the JSON body, matches field names and dotted paths against the operator's declared `internal/sensitivity` rules, and splits what it finds by whether the agent actually holds a data grant for that field: a granted sensitive field is recorded, an ungranted one is a finding and is scored into the same risk total the request side feeds, so an agent pulling fields nobody granted accumulates toward containment instead of producing a log line. Array indices are dropped from the path so a thousand rows report `customers.ssn` once, and the walk is bounded in both depth and field count because a response body is attacker-influenced input on the hot path. It audits and scores rather than blocking, deliberately: by the time this runs the downstream has already produced the data and it is on its way back, so refusing at that point would be theatre, and actually preventing it means either declaring the resource up front so the request-side data-grant check refuses the call, which already works, or filtering responses field by field, which would mean NIA deciding what an agent may see rather than what it may call. The limit is the same one `internal/sensitivity` states for itself: this matches declared names, not values, so it will not recognize a social security number by its shape and says nothing about a field nobody declared, which makes it exactly as complete as the rules are and explainable in the same way. The test that matters asserts the finding reaches containment, by setting a kill threshold the response-side score crosses and confirming the agent ends up killed.

- Phase 30: tools and data resources became real types in the authorization model, which is the item phase 18 explicitly deferred as cross-repo work. They used to reach OpenFGA smuggled into Tessera's `api_group` field as a prefixed string, first as `tool:{name}`, which OpenFGA rejected outright because an object id may not contain a colon, then as `tool/{name}`, which worked but meant the model could say nothing about them, they were api groups with awkward names. They are `tool:{name}` and `data:{name}` with a `granted` relation now, declared in `deployments/openfga-model.json`. The Tessera side deliberately did not grow NIA-specific grant kinds, which would make a generic authorization control plane agent-aware; it grew a generic typed-object grant (`object_type`, `object_id`, `relation`) so any caller whose objects are neither api groups nor endpoints can say so, and Tessera maps what it is given without knowing what it means. Two bugs fell out of actually running it, neither catchable against a fake server. Tessera now rejects a colon, hash, at sign or whitespace inside any component, because the original failure was OpenFGA refusing the object id and that belongs at the boundary with a message naming the field. And more seriously, Tessera's tuple read enumerated a hardcoded list of object types, since OpenFGA has no query shape for "everything this user touches regardless of type", so with a third type in play a kill read back no tool tuples, deleted none, and reported success while the client kept its access, and a reconcile could not see the existing tuples, tried to write them again, and had the whole batch refused as a duplicate. The types now come from the store's own authorization model, which is right by construction: whatever a caller can grant, the model has to declare or the write would fail. Verified end to end against a real OpenFGA and a rebuilt Tessera: grants stored as `tool:invoice.read#granted@client:...`, a kill confirmed to delete them, and the authorization check confirmed to go false immediately after. What this still does not give you is hierarchy, a `tool` object has one relation and no parent, so "granted on this tool group implies granted on its tools" is expressible now where it was not before, but nothing expresses it. The Tessera change lives in that repo's own commit, `cb84937`.

- Phase 31: the gateway terminates and understands MCP instead of tunnelling JSON. Serving MCP over streamable HTTP at `/mcp`, built on the official `modelcontextprotocol/go-sdk` rather than a hand-rolled protocol, the gateway authenticates the agent in the HTTP layer in front of the protocol, parses the operation, and only then decides. That ordering is the point: a gateway that forwards the agent's bytes can authenticate the connection and nothing else, it cannot tell `tools/call` from `tools/list` or see which tool and which arguments, which is every decision NIA exists to make. A `tools/call` runs the full pipeline, per-agent rate limit, catalog check, tool grant, resource-level data grants derived from the arguments, risk scoring and containment, and the decision completes before the downstream connection is opened, so a refused operation is never sent rather than sent and ignored. That pipeline now lives in one place, `decision.go`, used by both the REST and MCP front doors, because two front doors with two copies of the pipeline is how one of them quietly ends up missing a check. The downstream connection is separate and separately authenticated with NIA's own credential: the agent's credential authenticates the agent to NIA and stops there, since a downstream holding it could act as that agent against anything else that trusts it. Responses come back through the same inspection boundary the REST path uses, so a sensitive field the agent holds no grant for is a finding on this path too. The session model is stateless, so replicas share nothing and the gateway is safe behind a load balancer with no sticky routing; the cost is one downstream session per call and the limit is that MCP features needing session state are unavailable, which is documented rather than papered over with process-local affinity. Fifteen integration tests run against a real downstream MCP server built on the same SDK, not a stub, covering initialize and capability negotiation, invalid authentication, unauthorized and authorized calls, argument visibility to the policy layer, downstream errors, manual and risk-triggered kills, malformed JSON-RPC, method/tool mismatch, two independent gateway instances serving the same agent, and the credential never being forwarded. One honest protocol limitation found by running it: this SDK negotiates `initialize` inside the server before receiving middleware runs, so NIA audits the authenticated session at the transport layer instead of in the protocol middleware.

- Phase 32: real mutual TLS at the gateway. The gateway terminates TLS itself, which is the authoritative model here rather than trusting a certificate header from an ingress, and with a client CA bundle configured it verifies client certificates: chain, validity and signature are Go's TLS stack doing the thing a deployment relies on. The SHA-256 thumbprint is computed from the DER bytes of the certificate actually presented in the handshake, never from anything the caller sends, and `X-Client-Cert`, `X-Client-Cert-Thumbprint` and `X-Forwarded-Client-Cert` are not read anywhere in this codebase. The step that turns a certificate into an identity is an explicit binding: a certificate signed by a trusted CA means the deployment trusts that CA's issuance process, which is a different statement from "this certificate is agent X", and conflating the two would make every certificate that CA ever issues into an authenticated agent. So a valid but unbound certificate authenticates as nobody. A binding is modelled as a credential of kind `mtls_cert`, which is not a shortcut: it is the same revocable, expirable, killable thing every other credential is, so revocation, expiry, disable and the kill cascade all apply without a second implementation of each, and revoking the binding is the local revocation mechanism. CRL and OCSP are deliberately not implemented, because how a deployment distributes revocation information is a PKI decision this codebase should not make on its own. Certificate and bearer authentication coexist on one listener and produce the same resolved identity, so everything after authentication is identical and there is no certificate-specific authorization path that could be missing a control. Eleven tests do real TLS handshakes against a real listener with a real CA, covering a valid bound certificate, an unknown CA, an expired certificate, a broken chain, a valid certificate with no binding, binding to the right agent, headers failing to override the certificate identity, a revoked binding, the thumbprint coming from the presented certificate, a second certificate with the same subject failing to inherit a binding, and both mechanisms hitting the same authorization, grant and kill checks. One honest detail the tests turned up: Go's TLS client will not send a certificate that does not chain to the CAs the server advertises, so an untrusted certificate usually arrives as no certificate at all rather than as a failed handshake, and the test asserts the refusal rather than one particular mechanism of it.

- How phases 31 and 32 were verified end to end, on the real stack rather than through the test harness alone: Postgres, OpenFGA, a Tessera.Service container and a standalone real MCP server, with `nia-api` and `nia-gateway` as real processes. An agent was registered, granted `database.query`, and issued a credential. It then opened a real MCP connection to the gateway (`initialize` negotiated protocol `2026-07-28` with the tools capability advertised) and called the tool; the downstream MCP server's own log recorded the invocation and its response came back to the agent. The agent's behaviour then changed: it reached for `customers.ssn`, a critical resource it held no data grant for, and was refused with `agent is not authorized for resource "customers.ssn"` before the downstream was contacted at all. It then began hammering the tool it did have, `call_rate` fired, and on the fourth call the cumulative total crossed the kill threshold and `monitoring.kill` recorded "cumulative risk 5 crossed threshold, killed, revoked 1 active credential(s)". `GET /agents/{ref}` then reported `effective_state=killed` from the live sentinel while the registry cache still said `active`, which is phase 26 catching a kill that happened in the other process. The next MCP request was refused at `initialize` with Unauthorized, and the downstream server's log shows it received exactly the five invocations that were authorized and none after the kill. The audit trail, written by both processes into one Postgres, verified clean across 38 events, was anchored with a signed checkpoint, and then, after deliberately rewriting the `monitoring.kill` row with SQL, verification reported `OK=false` naming the exact event. Separately, `niactl credential bind-cert` derived a thumbprint that matched `openssl x509 -fingerprint -sha256` on the same certificate, character for character.

## Layout

```
cmd/api        control-plane API: registration, inventory, credentials, grants, kill switch
cmd/gateway    Agent/MCP gateway: the hot path, resolve -> check -> forward
cmd/niactl     operator CLI, talks to cmd/api over HTTP (and cmd/gateway directly for gateway call / simulate attack)
internal/      identity, registry, credentials, policy, audit, risk, monitoring, incident, graph, metrics
deployments/   Dockerfiles, docker-compose, and the OpenFGA store/model bootstrap for local dev
docs/          architecture, data model, threat model, and security invariants
```

## Running locally

```bash
go build ./...
go vet ./...
go test ./...

# in one terminal
go run ./cmd/api

# in another
go run ./cmd/gateway

# register an agent
go run ./cmd/niactl register -ref agent:billing-reconciler -owner bogdan -purpose "reconciles invoices nightly"

# list what's registered
go run ./cmd/niactl list

# register a tool it's allowed to call
go run ./cmd/niactl tool register -name invoice-lookup -transport http -risk read_only -owner bogdan

# issue it a credential
go run ./cmd/niactl credential issue -ref agent:billing-reconciler -kind api_key -ttl 24h

# revoke one key without touching the agent itself
go run ./cmd/niactl credential revoke -id <credential_id> -reason "key leaked in a log"

# pull the kill switch, the bigger hammer, for when the agent itself is compromised
go run ./cmd/niactl kill -ref agent:billing-reconciler -incident INC-001

# review what happened to it
go run ./cmd/niactl audit -ref agent:billing-reconciler

# grant the agent access to that tool, the register and grant calls above already added both
# to the identity graph on their own, agent registration and tool registration add their own
# nodes, this grant adds the edge between them, nothing here needs graph add-node/add-edge by hand
go run ./cmd/niactl grant write -ref agent:billing-reconciler -kind tool -object invoice-lookup

# what could this agent reach if it were compromised right now
go run ./cmd/niactl graph reachable -id agent:billing-reconciler

# the same question, summarized: total reachable, a count by kind, and a HIGH/MEDIUM/LOW severity call
go run ./cmd/niactl graph blast-radius -id agent:billing-reconciler

# add a human as the accountable owner, nothing else creates Human nodes on its own
go run ./cmd/niactl graph add-node -id human:bogdan -kind human
go run ./cmd/niactl graph add-edge -from human:bogdan -to agent:billing-reconciler -kind owns

# call the gateway directly the way an MCP-aware caller would
go run ./cmd/niactl gateway call -ref agent:billing-reconciler -tool invoice-lookup

# drive the whole loop end to end: registration, grants, a scripted attack sequence,
# and, if the gateway was started with NIA_RISK_FLAG_AT / NIA_RISK_REVOKE_AT / NIA_RISK_KILL_AT
# set low enough, a real kill partway through and a real denial on the next call
go run ./cmd/niactl simulate attack -scenario agent-hijack

# review the structured incident records that scenario's containment decisions created
# (only meaningful if the gateway had risk thresholds set, see above)
go run ./cmd/niactl incident list -ref agent:invoice-agent

# one report: identity, credentials, grants, recent audit, blast radius, and a
# best-effort look at the gateway's own risk view for this agent, all in one place
go run ./cmd/niactl agent inspect -ref agent:billing-reconciler

# just the gateway's risk view: cumulative risk, thresholds, recent incidents
go run ./cmd/niactl risk -ref agent:billing-reconciler

# scrape either process's counters and gauges directly
curl http://localhost:8080/metrics
curl http://localhost:8081/metrics
```

Most of the commands above run fine against the in-memory policy client, the default, no Tessera, OpenFGA, or Postgres required, because they only ever talk to `cmd/api`. `gateway call` and `simulate attack` are the exception, worth being precise about rather than leaving as an assumption: `cmd/api` and `cmd/gateway` are two separate OS processes, and the in-memory default is exactly that, in-memory, private to whichever process constructed it. Point both at the unconfigured default and a grant written through `cmd/api` is invisible to `cmd/gateway`'s own policy check, every gateway call comes back 403, not because anything is broken, because there's genuinely nothing shared between them to check against. `niactl register` / `grant write` / `kill` and the rest still work standalone against `cmd/api` either way, it's specifically the two-process, grant-then-call-the-gateway path that needs a real shared backend. Tessera is that backend, and it doesn't need OpenFGA behind it to serve that purpose: point both `cmd/api` and `cmd/gateway` at one running `Tessera.Service` (`NIA_TESSERA_BASE_URL`, the same `NIA_TESSERA_JWT_SIGNING_KEY` it was started with, and, only if it isn't running with its own defaults, `NIA_TESSERA_JWT_ISSUER` / `NIA_TESSERA_JWT_AUDIENCE`) and Tessera's own `InMemoryAuthorizationStore` fallback (unset `OPENFGA_API_URL`) is enough of a shared backend for `gateway call` and `simulate attack` to actually work end to end, no live OpenFGA needed, that's how the "See it work" transcript above was captured. See `internal/policy/from_env.go` for the full env var list and defaults.

The same two-process gap exists for credentials now that `credentialResolver` is the gateway's default resolver, found while verifying this pass rather than assumed: `credentials.FromEnv` follows the exact same "unset means a private in-memory default" pattern `policy.FromEnv` does, so a credential issued through `cmd/api` (`credential issue`, or `simulate attack`'s own setup step) is invisible to `cmd/gateway`'s `credentialResolver.Verify`, every gateway call gets a 401 "could not resolve caller identity", again not because anything is broken, because there's nothing shared to verify against. Set `NIA_CREDENTIALS_DATABASE_URL` to the same Postgres connection string on both `cmd/api` and `cmd/gateway` to fix it, confirmed against the local Postgres this was verified with: register an agent, issue it a credential through `cmd/api`, present that credential to `cmd/gateway`, get a real 200, kill the agent through `cmd/api`, present the same credential again, get a real 401, restore, confirm `GET /agents/{ref}` reports active again. `deployments/docker-compose.yml` below already points both services at the stack's shared `postgres`, so this is only something to notice running the two processes by hand outside compose.

`deployments/docker-compose.yml` brings up the full stack, NIA's two services plus Tessera, OpenFGA, and Postgres, see the Status section above for what's actually been confirmed. OpenFGA needs a store and an authorization model before Tessera can use it, which can't be baked into compose (a store only gets an id once OpenFGA is already running): bring up `postgres` and `openfga` first, run `deployments/bootstrap-openfga.sh`, add the store id it prints to `.env` as `TESSERA_OPENFGA_STORE_ID`, then bring up the rest. The stack's `postgres` service also now backs the audit trail (`NIA_AUDIT_DATABASE_URL`, hardcoded in `docker-compose.yml`, it isn't a secret), no extra setup needed for that part, just `go mod tidy` first if this is the first build since `internal/audit/postgres_sink.go` was added, it pulls in `lib/pq`.
