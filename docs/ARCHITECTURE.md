# NIA: Non-Human Identity & Agent Security

## An Agent Security Control Plane

### The problem

An AI agent isn't just software anymore. It holds credentials, gets granted permissions, calls tools, reaches into data it was never explicitly handed, and takes actions on its own initiative, sometimes on behalf of a human, sometimes on behalf of another agent. Once you have more than a couple of these running, three questions stop having obvious answers: what is this agent actually allowed to do, who authorised it to do that, and if it starts doing something it shouldn't, how do you stop it in the next second instead of the next deploy.

NIA treats every agent, service account, and automated identity as a first-class non-human identity (NHI) with its own registration, its own credentials, its own permission graph, and its own kill switch. It's modelled on how you'd run IAM for humans, because underneath it's the same problem: know who's asking, decide if they're allowed, watch what they do, and be able to cut them off immediately when something's wrong.

### Why this isn't a green-field design

Most of the hard part of this already exists and works: Tessera. It's the relationship-based authorization control plane I built on OpenFGA, doing live per-request authorization checks and a surgical kill switch, delete a tuple, the next check denies, no token revocation, no redeploy. That's the Policy Engine, Authorization, Credential Revocation, and Kill Switch boxes in the brief, already solved. NIA doesn't reinvent that layer, it generalizes it: Tessera's `client_ref` becomes NIA's agent identity, Tessera's `Grant` becomes NIA's permission, and Tessera's design invariants (sentinel-first kill, idempotent reconcile, one canonical form, per-client mutual exclusion) carry over unchanged. What NIA adds is everything Tessera was never scoped to do: agent registration and lifecycle, tool and MCP awareness, credential issuance (not just identity resolution), risk scoring, runtime behavioral monitoring, agent-to-agent trust, delegation, and an identity graph tying humans, agents, tools, and data together.

### The two planes

Same split Tessera already uses, carried up a level.

```
                                   HUMAN
                                     │
                                     ▼
                    ┌────────────────────────────────┐
                    │        NIA CONTROL PLANE        │   Go, this repo
                    │  registration, identity,        │
                    │  credentials, tool registry,    │
                    │  risk scoring, audit,           │
                    │  identity graph, delegation      │
                    └────────────────┬─────────────────┘
                                     │ declares grants, issues creds,
                                     │ manages the identity graph
                                     ▼
                    ┌────────────────────────────────┐
                    │            TESSERA               │   .NET, existing repo
                    │  reconciles grants -> OpenFGA    │
                    │  tuples, kill switch, sentinel   │
                    └────────────────┬─────────────────┘
                                     │ writes/deletes tuples
                                     ▼
                              ┌─────────────┐
                              │   OpenFGA   │   relationship checks
                              └──────┬──────┘
                                     │ allow / deny, live, every request
                                     ▼
        ┌───────────────────────────────────────────────────┐
        │              AGENT / MCP GATEWAY (hot path)         │   Go, this repo
        │   resolves agent identity, checks OpenFGA,          │
        │   forwards or blocks, streams to monitoring         │
        └───────────┬────────────────────────┬────────────────┘
                    │                        │
               ┌────▼────┐              ┌────▼────┐
               │  Tools  │              │  Data   │
               └─────────┘              └─────────┘
                                     │
                                     ▼
                    ┌────────────────────────────────┐
                    │            MONITORING            │
                    │   risk scoring, anomaly detect   │
                    └────────────────┬─────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │   Detect / Block     │
                          └──────────┬───────────┘
                                     │
                          ┌──────────▼──────────┐
                          │   Revoke / Kill      │───▶ back to Tessera
                          └──────────────────────┘
```

The rule that makes Tessera work applies here too: the control plane never sits on the hot path. The gateway checks OpenFGA directly on every request. NIA's control plane and Tessera only manage the state those checks read, who exists, what they're allowed, and whether they've been killed. That's what makes the kill switch instant. It's a state change, not a code path change.

### The seventeen MVP items, mapped to modules

The brief lists seventeen things to build. None of them are new categories, they're all one of: identity, policy, enforcement, or observability. Here's where each one lives.

| MVP item | Module | Notes |
|---|---|---|
| Agent registration | `internal/registry` | Onboards a new `AgentRef`, mirrors Tessera's `ClientProvisioner` |
| NHI inventory | `internal/registry` | `GET /agents` and `niactl list` return every registered `AgentRef`. This is a full, unfiltered dump of `InMemoryAgentRegistry`'s map today, not a queryable search index, filtering or paging over a large fleet would need real storage behind it, which is why `internal/store` isn't listed here, that package doesn't exist yet, add it once a real filter need shows up rather than building it speculatively |
| Agent identity | `internal/identity` | Canonical `AgentRef`, assurance level, lifecycle state (active/suspended/killed). `identity.Resolver` is what turns an inbound request into one of these, `cmd/gateway`'s default implementation is `credentialResolver`, see the Credentials row below and "Credential-backed authentication and state convergence" |
| Credentials | `internal/credentials` | Issuance, rotation, binding of API keys, short-lived tokens, mTLS certs to an `AgentRef`. Tessera assumes credentials already exist and only resolves them, NIA owns the credential lifecycle itself. A credential is a real bearer secret now, not just a database row: `Issue` and `Rotate` return a 32-byte random secret exactly once, only its SHA-256 digest is ever stored, and `Verify` checks a presented secret against that digest with a constant-time comparison. Four real states, `Active`, `Revoked` (terminal), `Expired` (computed off `Credential.Effective(now)`, not a background sweep), `Disabled` (a reversible administrative pause, distinct from a revoke). Wired into `cmd/api` (`POST /agents/{ref}/credentials`, `GET` to list, plus `/disable`, `/enable`, `/rotate`, `/revoke`) and `niactl credential issue` / `list` / `disable` / `enable` / `rotate` / `revoke`, backed by `credentials.FromEnv` the same way `internal/audit` and `internal/policy` pick a Postgres or in-memory implementation off an env var (`NIA_CREDENTIALS_DATABASE_URL`), verified with `go test ./... -race` and, for the Postgres store specifically, a live test against a real database (`internal/credentials/postgres_live_test.go`, `NIA_CREDENTIALS_TEST_DATABASE_URL`) |
| Permissions | `internal/policy` | Thin Go client over Tessera's `Grant` model (api_group or endpoint-level grants), extended with tool and data scoped grants. `WriteGrants`/`DeleteGrants`/`ListGrants` have always existed on the client itself; they only reached `cmd/api` (`POST`/`DELETE`/`GET /agents/{ref}/grants`) and `niactl grant write` / `delete` / `list` in this pass, before that there was no way to actually grant an agent a permission through the control-plane API at all, verified with `go test ./... -race` |
| Tool registration | `internal/registry/tools` (sub-package) | Catalog of callable tools, each with a risk classification. Wired into `cmd/api` (`POST /tools`, `GET /tools`, `GET /tools/{name}`) and `niactl tool register` / `list` / `get`, verified with `go test ./... -race`. The gateway consults this catalog now too, see the MCP integration row below |
| MCP integration | `cmd/gateway` | MCP-aware transport in the gateway, intercepts tool-call requests, resolves the calling agent, checks policy before invoking. When `NIA_TOOLS_API_URL` is set, a step is inserted in front: look the tool up in `cmd/api`'s catalog over HTTP, reject with 404 before ever reaching the policy check if nobody registered it. When `NIA_GATEWAY_RESOURCE_RULES_PATH` is also set, a second step follows the tool-level check: the call's arguments are turned into resource object names and any classified `sensitive` or above needs its own `data` grant, see "Resource sensitivity" below. Both unset, behavior is unchanged, additive rather than a stricter default nothing opted into. See `tools.HTTPReader`, `tools.FromEnvReader`, and `cmd/gateway/resources.go` |
| Policy engine | **Tessera** (external) | Not rebuilt. NIA's `internal/policy` is a client for it |
| Authorization decisions | OpenFGA, via Tessera's `IAuthorizationStore.CheckAsync` | Live, per-request, no cache |
| Audit trail | `internal/audit` | Append-only sink. Gateway decisions and registry changes both write here now, one event shape either way; Tessera's own `AuditEvent`s still don't, no bridge exists yet. `PostgresSink` gives it a real, shared backend, confirmed against a live stack, `nia-api` and `nia-gateway` reading and writing the same table, see "What this scaffold is, and isn't" |
| Risk scoring | `internal/risk` | New. Scores agents and individual calls off signals: novel tool use, sensitive data touched, deviation from historical pattern. `HistoryScorer` is the first real `Scorer`, three signals now, novel-tool detection, a risk-class-weighted signal off the tool catalog, and a sensitive-resource signal off `internal/sensitivity` when a call's arguments touched anything classified `sensitive` or above. Not CENTIPEDE's anomaly detection yet, that's still the intended eventual replacement, and `volume_deviation` still needs rate tracking this scaffold doesn't have. Verified with `go test ./... -race` |
| Runtime monitoring | `internal/monitoring` | Consumes the gateway's request stream, feeds the risk engine, raises detect/block signals. Wired into `cmd/gateway`: every allowed call is scored and observed when `NIA_RISK_FLAG_AT` / `NIA_RISK_REVOKE_AT` / `NIA_RISK_KILL_AT` is set, unset means monitoring is skipped entirely. Thresholds compare against a running per-agent total now, not a single call's score in isolation, `Monitor.Observe` accumulates every scored call into `cumulative[agentRef]` and only resets it on a kill, a flag or a revoke leaves the total in place, see `Monitor`'s own doc comment for why a kill is the one action that justifies starting over. `ActionRevoke` actually revokes, every active credential for the agent via `internal/credentials.Store`, though `cmd/gateway` itself has no credential store wired in yet, so a revoke threshold crossed there degrades to an audited no-op. The gateway's own tool-call response now carries a `risk` block, this call's value and signals plus the agent's current cumulative total and whatever action fired, when monitoring is configured, so a caller doesn't have to separately query for what just happened. Every flag, revoke, or kill also creates a structured `internal/incident` record now, not just an audit line, see "Structured incident evidence" below. A kill here is a real state change, `internal/policy.Kill` genuinely denies the next call, confirmed by actually running the attack scenario end to end. This used to be scoped to `internal/policy`'s own state and nothing else: `handleKill` sets `AgentRegistry.State` because it runs inside `cmd/api`, but an automatic kill fires inside `cmd/gateway` and had no path back to that registry, so `GET /agents/{ref}` and `niactl agent inspect` could report an agent as `active` after monitoring had already killed it in every way the gateway itself respected. Closed now without adding a new cross-process push, `handleGetAgent` live-queries `policy.Client.IsKilled` on every read instead of trusting the registry's cached `State`, see "Credential-backed authentication and state convergence" below for the full reasoning. `ActionKill` also now revokes every active credential for the agent, the same `revokeCredentials` helper `ActionRevoke` already used, closing the matching gap where a killed agent's credentials kept reporting `Active` forever even though every authorization check already denied them. Verified with `go test ./... -race`, including a concurrency test that fires fifty simultaneous calls for one agent and checks the total lost no updates |
| Credential revocation | `internal/credentials` (revoke path) | Distinct from the kill switch: revokes one credential without killing the whole identity. `POST /credentials/{id}/revoke` and `niactl credential revoke`, writes `credential.revoked` to the audit trail same as every other control-plane action, verified with `go test ./... -race` |
| Kill switch | Tessera's `KillSwitchService`, called from `internal/policy` | Reused as-is: sentinel-first delete, confirmed, one client, nothing else touched |
| Agent-to-agent trust | `internal/graph` | `trusts` edges between `AgentRef`s, recorded and queried through `POST /graph/edges` and `niactl graph add-edge`. This is bookkeeping the graph can answer questions about, not yet something the gateway's live authorization check consults, see the Delegation row below for the same gap |
| Delegation | `internal/graph` + `internal/policy` | `delegates_to` edges are recorded and queryable the same way `trusts` is, wired into `cmd/api` and `niactl`, verified with `go test ./... -race`. Layering `delegate` onto OpenFGA as a relation Tessera's own checks understand, so a delegation edge actually changes what the gateway allows rather than only what the graph reports after the fact, is still open, `internal/policy` doesn't consult `internal/graph` today |
| Basic identity graph | `internal/graph` | The graph tying humans, agents, tools, and data together, the thing you query when you need blast-radius analysis after an incident. Wired into `cmd/api` (`POST /graph/nodes`, `POST /graph/edges`, `GET /graph/{id}/neighbors?kind=`, `GET /graph/{id}/reachable?kinds=`, `GET /graph/{id}/blast-radius?kinds=`) and `niactl graph add-node` / `add-edge` / `neighbors` / `reachable` / `blast-radius`, verified with `go test ./... -race`. `reachable` and `blast-radius` both default to every edge kind when `-kinds` is omitted, the blast-radius question usually means "everything, however it's reachable," not one relation at a time. Agent registration, tool registration, credential issuance, and grant writes all add their own nodes and edges to the graph now, see "The identity graph" below for what that closes and what it doesn't |

### The identity graph

This is the part Tessera doesn't have, because Tessera only ever needed to know about one kind of node (a client) and one kind of edge (a grant). NIA needs more of both, because "what can this agent reach, transitively, through delegation and trust" is a graph question, not a lookup.

Nodes: `Human`, `Agent` (the NHI itself), `Tool`, `DataResource`, `Credential`.

Edges: `owns` (Human owns Agent), `delegates_to` (Agent delegates to Agent, time-bounded), `trusts` (Agent trusts Agent, for agent-to-agent calls), `member_of` (Agent member of a group, same shape as Tessera's `bu_group`), `grants` (Agent granted access to Tool or DataResource, same shape as Tessera's endpoint/api_group grants), `bound_to` (Credential bound to Agent).

This graph is queryable independently of the live OpenFGA checks. OpenFGA answers "can X do Y right now." The identity graph answers "everything X could reach, directly or transitively," which is what you actually want when doing incident response on a compromised agent, or when figuring out the blast radius before granting something new.

Until this phase, that graph stayed empty unless an operator populated it by hand through `niactl graph add-node`/`add-edge`, which meant a blast-radius query on a freshly registered agent came back empty even though the control plane already knew that agent existed. It's auto-populated now, from what `cmd/api` already knows: registering an agent adds its `Agent` node, registering a tool adds its `Tool` node, issuing a credential adds a `Credential` node and a `bound_to` edge to the agent it was issued for, and writing a tool or data grant adds a `grants` edge from the agent to the object, creating the object's node first if nothing had registered it yet. `api_group` and `endpoint` grants are skipped, neither has a natural graph node on either side. All of this is fail-open the same way audit writes are, a graph write failing doesn't fail the request that triggered it, it's logged and the graph is left slightly behind, not the operation that actually mattered.

One gap is deliberately not closed here: `internal/graph.Graph` has no edge-removal primitive, so deleting a grant through `DELETE /agents/{ref}/grants` does not remove the matching `grants` edge, the graph stays a superset after a revoke rather than a stale-safe mirror. `internal/policy`'s own `ListGrants` is still the source of truth for what's currently granted, the graph is for reachability, not a live permission list. Closing this needs an edge-removal method added to the `Graph` interface and both implementers, deferred rather than folded into this pass, and called out here, in `niactl`'s own usage text, and in `graphAddGrantEdges`'s doc comment so it's not a silent surprise.

`GET /graph/{id}/blast-radius` (`niactl graph blast-radius -id <node_id>`) turns a `Reachable` traversal into the summary an incident review actually wants first: total reachable nodes, a count by kind, which reachable data resources classify `sensitive` or `critical` through `internal/sensitivity` (empty, not an error, when `NIA_SENSITIVITY_RULES_PATH` isn't set), and a severity call, `HIGH`, `MEDIUM`, or `LOW`. The rule is fixed and stated plainly rather than tuned: `HIGH` if anything reachable is classified critical, or five or more reachable nodes are themselves agents or tools, a wide blast radius of controllable things even without touching flagged data; `MEDIUM` if anything reachable is classified sensitive, or at least one reachable node is an agent or tool; `LOW` otherwise. Same posture as `internal/sensitivity`'s own classification, explainable over sophisticated, an operator can point at the exact count or the exact resource that produced a given severity.

### Resource sensitivity

`internal/sensitivity` answers a narrower question than the identity graph: given a resource name, a tool argument, a column, a field, a data object, how sensitive is it. Five levels, `public`, `internal`, `confidential`, `sensitive`, `critical`, `public` being the zero value and the default for anything nobody declared a rule for. This is deliberately a flat rule list, not inference: an operator writes "customer.ssn is critical," the classifier looks it up, first matching rule wins. That's what makes it explainable, an incident review can point at the exact rule that made a call get flagged, not a model's guess.

The point of this package is to name resources the same way `policy.GrantForData` already does, `GrantForData("customer.ssn")` is an authorization grant naming that resource, a `sensitivity.Rule{Pattern: "customer.ssn", Level: sensitivity.Critical}` is a classification of the same name. The two are meant to be read together: an agent can be granted `database.query` as a tool while still lacking the data grant for `customer.ssn`, which is what makes "authorized to call the tool, not authorized to touch this column" enforceable without inventing a second authorization system, `internal/policy`'s existing `data` grant kind already covers it, see "The seventeen MVP items" table above.

Wired in now: `POST /tools/{tool}/call` decodes an optional `arguments` object from the request body (see `cmd/gateway`'s `toolCallRequest`), an `ArgumentResourcePolicy` (`cmd/gateway/resources.go`, `NIA_GATEWAY_RESOURCE_RULES_PATH`) turns those arguments into the resource object names they touch, and any resource classified at `sensitive` or above needs its own `policy.GrantForData` grant, checked and audited the same way the tool-level grant is, `gateway.denied` with the specific resource named in the detail if it's missing. `internal/risk.HistoryScorer` also takes a `sensitivity.Classifier` now and adds a `sensitive_resource` signal, weighted higher again when the level is `critical`, when a scored call's `CallContext.Resources` includes anything at or above that threshold. All three env vars, `NIA_GATEWAY_RESOURCE_RULES_PATH`, `NIA_SENSITIVITY_RULES_PATH`, and the risk/monitoring thresholds, are independently optional, unset means the step it gates doesn't run, same additive posture as the tool catalog check before it.

### Attack simulation

`niactl simulate attack -scenario agent-hijack` is a deterministic, scripted scenario runner (`cmd/niactl/simulate.go`), not printed output standing in for one. It registers a real agent and a real tool catalog through `cmd/api`, writes real starting grants, then drives a sequence of real `POST /tools/{tool}/call` requests through `cmd/gateway`, the same request an MCP-aware caller would send, and prints what actually came back.

The one scenario today, `agent-hijack`, models an invoice-processing agent that's authorized (coarsely, at the tool level) for more than its normal work ever uses, a realistic over-privileged setup: broad RBAC says yes, behavioral signals are what actually catch the escalation. It's granted all seven tools up front, but `customers.ssn` is deliberately left ungranted at the data level, so its own step, a `database.query` call naming that column, gets a real, separate 403 from the gateway's argument inspection (see "Resource sensitivity" above), not just a risk flag, proving the Agent+Tool+Resource decision actually enforces something, not only the Agent+Tool one. The later steps escalate through tools the agent is authorized for but has never used, `customer.export`, `credential.read`, `external.upload`, exactly what `HistoryScorer`'s `novel_tool` and risk-class signals exist to catch: authorized, allowed, and still worth flagging.

Whether containment actually fired is read off the transcript itself, not asserted separately: the scenario's last step re-calls a tool the agent was granted and had already used successfully earlier in the same run, and if monitoring was configured with low enough thresholds to have killed the agent by then, that same call now comes back 403, `policy.Check` denying it because the kill sentinel is now in effect, not because anything about the request changed. That's an actual state transition, not a printed result, the same kill path `niactl kill` drives by hand.

Monitoring is opt-in the same way everywhere else in this codebase is: run the scenario against a gateway started without `NIA_RISK_FLAG_AT` / `NIA_RISK_REVOKE_AT` / `NIA_RISK_KILL_AT` set and every step comes back allowed, no risk block, no containment, that's an honest result too, it says the demo needs monitoring turned on, not that the pipeline is broken. `cmd/niactl/simulate.go`'s own tests (`cmd/niactl/simulate_test.go`) exercise the scenario's own well-formedness (every tool a step or grant names is actually registered) and drive `runScenario` against fake `cmd/api` and `cmd/gateway` HTTP servers standing in for the real processes, asserting on the actual call sequence and the containment-detection logic, not just describing it.

### Credential-backed authentication and state convergence

Before this pass, the gateway trusted an `X-Agent-Ref` header at face value. `headerResolver` read whatever a caller sent, looked up nothing, checked nothing, and handed the result straight to authorization as though it were an authenticated fact. Anyone who could set an HTTP header could call any tool as any agent, the entire authorization layer behind it was sound, OpenFGA, grants, resource sensitivity, all of it, and none of it mattered because the identity feeding it was unauthenticated input. This was found during a security review of the runtime path, not reported by anyone, and it's the reason this section exists.

`cmd/gateway/authn.go`'s `credentialResolver` is the fix, and it's now the gateway's default `identity.Resolver`, `headerResolver` still exists but only runs when `NIA_GATEWAY_INSECURE_HEADER_AUTH=1` is set, a loud, opt-in-only escape hatch for local dev, logged at startup so it can't be silently on in a real deployment. A caller presents `Authorization: Bearer <credential-id>.<secret>`. The id half finds the row, the secret half is checked against `credentials.Store.Verify`'s stored SHA-256 digest with `crypto/subtle.ConstantTimeCompare`, not a plain `==`, timing matters once a secret comparison is on a network-reachable path. `Verify` itself already refuses anything whose `Credential.Effective(now)` isn't `Active`, so a revoked, expired, or disabled credential fails authentication, not just a later authorization check, the three lifecycle states in the Credentials row above now have real runtime teeth. `credentialResolver` then makes one more call `Verify` alone can't: `policy.Client.IsKilled` on the credential's owning agent, independently of whatever the credential's own row says. This is deliberate defense in depth, if a deployment somehow has a `credentials.Store` that's out of sync with the real kill state, Tessera/OpenFGA (via `policy.Client`) is still the one thing everything else in this system already treats as authoritative, so it's what authentication checks too, not just authorization. Every failure mode here, wrong secret, unknown id, revoked, expired, disabled, killed agent, collapses to the same `(nil, nil)` "unresolved" result and the same 401, an attacker probing which specific reason a credential failed gets no signal to work with. A genuine infrastructure failure, the credential store or the policy client not answering at all, is different and returns a real error instead, `identity.Resolver`'s own doc comment states the contract plainly: `(nil, nil)` is "no identity, and that's not an error," a non-nil error is "the question couldn't be answered," and the gateway turns the first into 401 and the second into 500, never into an implicit allow.

The same kill-state authority closes a second, related gap: `GET /agents/{ref}` and `niactl agent inspect` used to read `AgentRegistry.State` alone, a cache `handleKill` updates on a manual kill but that an automatic kill from `internal/monitoring` (running inside `cmd/gateway`, a different process) had no way to reach. Rather than adding a new cross-process push, `internal/monitoring` calling `cmd/api` over HTTP on every automatic kill, which would mean the containment path itself now depends on a second service being up, `handleGetAgent` live-queries `policy.Client.IsKilled` on every read and overrides the reported `EffectiveState` to `killed` when it says so, using the `policy.Client` both processes already share as the one source of truth instead of trying to keep two caches in sync. `KillSentinelChecked` in the response says whether that live check actually succeeded, a caller can tell "we confirmed this against real enforcement state" apart from "we're showing you a possibly-stale cache because the policy client didn't answer," rather than the two looking identical. `AgentRegistry.State` still gets updated on a manual kill, that's not removed, it just isn't what `handleGetAgent` trusts anymore, it only keeps the cache from being needlessly wrong in between live queries and whatever else in the codebase still reads the registry directly.

Kill convergence extends to credentials too: both kill paths, `handleKill` (manual, in `cmd/api`) and `Monitor.Observe`'s `ActionKill` case (automatic, in `cmd/gateway`), now call a `revokeAllCredentials`-shaped helper that revokes every credential whose `Effective(now)` is still `Active` for the killed agent, so a kill converges identity state, policy state, and credential state together instead of only the first two. This was a real gap before this pass: `ActionKill` touched `internal/policy` and nothing else, a killed agent's credentials kept reporting `Active` in `credentials.Store` forever, even though `credentialResolver`'s own independent `IsKilled` check meant they could never actually authenticate again either. Both places are best-effort and fail open the same way `s.audit` and the graph auto-population already do, a single credential's revoke failing is logged and the loop continues, the kill itself already happened and is what actually matters, see `revokeAllCredentials`'s and `Monitor.revokeCredentials`'s own doc comments.

What this doesn't cover, stated plainly: `credentialResolver` only guards the gateway's tool-call path, `cmd/api` itself had no equivalent until the next section below closed that gap separately. And `credentials.Store.Enable`, the Postgres implementation specifically, has a small theoretical race between its status read and its update, documented in the method's own comment, real but low-severity, the caller has to already know a credential's id, this isn't a way to enable something you couldn't otherwise touch.

### Operator authentication for the control plane

The gap named above, `cmd/api`'s own twenty-odd endpoints having no authentication at all, was closed separately, after the credential work above, because it's a different problem with a different shape. `credentialResolver` authenticates an agent (an NHI) calling the gateway to run a tool. Nothing in this system authenticated a human or a service calling `cmd/api` to register an agent, issue a credential, write a grant, or kill something. Every `operator`, `revoked_by`, `disabled_by`, `enabled_by`, and `rotated_by` field across every handler was client-supplied free text, written straight into the audit trail. Anyone who could reach `cmd/api` over the network could kill any agent and have the audit trail say whoever they typed into the request body did it.

`internal/opauth` is the fix, and it's deliberately narrower than `internal/credentials`: a static, admin-managed list of bearer tokens mapped to operator names, loaded once from a JSON file named by `NIA_OPERATOR_TOKENS_PATH`, each token's SHA-256 digest kept in memory, never the plaintext. `opauth.FromEnv()` returns `(nil, nil)` when that env var is unset, not a safe empty store, there's no such thing here: an empty `StaticStore` would reject every caller, indistinguishable from a deployment that locked itself out, so the package makes "unconfigured" and "configured with zero tokens" different states on purpose, the latter is a startup error. `cmd/api/opauth.go`'s `operatorAuthMiddleware` wraps the whole mux, every route except `GET /healthz` and `GET /metrics` requires `Authorization: Bearer <token>`, but only when `server.opStore` is non-nil, the same opt-in-by-env-var posture every other feature in this codebase follows. `routes()` had to change its declared return type from `*http.ServeMux` to `http.Handler` to make this possible, every call site only ever calls `.ServeHTTP` on the result, so this is source-compatible, not a behavioral change on its own.

The actual security property is `resolveOperator(ctx, claimed string) string`: when opauth is configured and the request authenticated, it returns the token's real operator name, ignoring whatever the request body claims in its `operator`/`*_by` field entirely. When opauth is unconfigured, it falls through to the claimed value unchanged, so a deployment that hasn't turned this on gets exactly the old behavior, nothing silently tightens underneath it. Every handler that writes an audit event with an operator field now calls `resolveOperator` first, `handleKill`, `handleRestore`, `handleIssueCredential`, `handleRevokeCredential`, `handleDisableCredential`, `handleEnableCredential`, `handleRotateCredential`, `handleWriteGrants`, `handleDeleteGrants`. `cmd/api/opauth_test.go`'s `TestHandleKill_AuthenticatedOperatorOverridesTheClaimedOneInTheAuditTrail` is the test that states this directly: authenticate as a token belonging to `bogdan`, send a kill request whose body claims `"operator":"someone-else-entirely"`, read the resulting audit event back, it says `bogdan`. Verified the same way against a real running process too, not only in the test suite, a live `nia-api` with `NIA_OPERATOR_TOKENS_PATH` set, driven with real `curl` and `niactl` requests, confirmed the same spoofed-body-loses behavior end to end.

What this doesn't cover, named the same way the rest of this document names its gaps: no per-operator authorization or scoping, every valid token can call every endpoint, this is authentication, not RBAC, an authenticated operator who shouldn't be allowed to kill agents can still kill agents. No live rotation or revocation, changing the token file means editing it and restarting the process, there's no equivalent of `credentials.Store.Revoke` here. `TesseraHTTPClient` still doesn't carry per-operator identity through to Tessera itself, so a Tessera-side audit trail, if one existed, wouldn't show which NIA operator triggered a given Tessera call, only that NIA called it. `niactl` reads its own token from `NIA_OPERATOR_TOKEN` and sends it automatically when set, but there's nothing forcing an operator to use `niactl` instead of hand-crafted requests that simply omit the header when opauth isn't configured, or that include a stolen token when it is, token theft here has the same consequences token theft anywhere has, this package doesn't add anything beyond what a bearer token normally provides.

### Downstream forwarding: the gateway as an enforcement proxy

Before this pass, `handleToolCall` stopped at the authorization decision. It resolved identity, checked the tool grant, checked resource-level grants, scored and monitored the call, and then returned its own stub response, `{"agent":..., "tool":..., "status":"allowed"}`, the same shape whether or not a real tool existed on the other side. The doc comment said so directly: "a real deployment forwards the request to the tool's actual transport here." That integration point had nothing behind it. This meant NIA could prove it decided correctly, but not that the decision connected to anything real, an incomplete story for a control plane whose whole point is mediating actual access, not just answering yes/no.

`cmd/gateway/forward.go`'s `Forwarder` closes that gap. `HTTPForwarder` POSTs the tool call, the same `toolCallRequest` shape a caller sends to the gateway itself, to `<NIA_GATEWAY_DOWNSTREAM_URL>/<tool>`, and returns exactly what came back, status code, body, and how long it took. `handleToolCall` calls it as the very last step, strictly after identity resolution, credential state, kill state, tool and resource authorization, and risk scoring have all already run and passed, there is no second, unguarded route to a downstream tool, `handleToolCall` is the only place `Forward` is ever called from. `g.forwarder == nil`, the default, unset `NIA_GATEWAY_DOWNSTREAM_URL`, is the pre-forwarding behavior unchanged: the gateway still makes and audits the exact same decision, it just stops there and returns its own response, exactly what every gateway before this pass did, this is additive, not a stricter default nothing opted into.

One configured downstream target for the whole gateway, not a per-tool routing table, is a stated simplification. `internal/registry/tools.Tool` has no endpoint field, adding per-tool downstream routing would mean extending the catalog schema and every place that constructs a `Tool`, a larger change than closing this specific gap needs, and a single shared target is what a deployment that puts one MCP router or one API gateway behind NIA looks like anyway. Splitting this per tool later is additive, not a redesign.

A response is inspected for a narrow, named set of security-relevant conditions, `inspectAndAuditDownstream` in `cmd/gateway/main.go`, not general content scanning: the downstream's own HTTP status (5xx becomes `gateway.downstream_error`, 4xx becomes `gateway.downstream_rejected`, otherwise `gateway.downstream_ok`), a top-level JSON `"error"` field in the body even when the status was 200 (`gateway.downstream_reported_error`, the same shape `internal/transport/http.WriteError` itself produces), and a response that hit the 10 MiB read cap (`gateway.downstream_response_truncated`, a tool suddenly returning far more data than usual is worth a look on its own). Every one of these carries the tool, credential, downstream status, duration, and response size into the audit trail, not just a generic "forwarded" line that can't tell the outcomes apart later. A downstream that can't be reached at all, a network failure, a timeout, a closed connection, is a different outcome again, audited as `gateway.downstream_unreachable` and returned to the caller as 502, distinct from every "we said no" branch earlier in the same handler, an authorized call that couldn't be delivered is not the same thing as a denial.

Verified two ways. `cmd/gateway/forward_test.go` covers `HTTPForwarder` directly against a real `httptest.Server`, request shape, status passthrough, the read cap, an unreachable downstream. `cmd/gateway/forward_integration_test.go` is what the hardening directive actually asked for: `TestForwarding_ValidAgent_ReachesARealDownstreamToolAndReturnsItsResponse` drives a real credential through `handleToolCall` against a real downstream HTTP server and asserts the response the caller gets back is the downstream's actual JSON, not a stand-in; `TestForwarding_KilledAgent_DeniedBeforeDownstreamIsEverContacted`, `TestForwarding_RevokedCredential_DeniedBeforeDownstreamIsEverContacted`, and `TestForwarding_ToolDenied_DeniedBeforeDownstreamIsEverContacted` each assert the downstream's own call counter stays at zero when the request should never have gotten that far, the actual proof that a killed or revoked agent has no alternate path to a real tool, not just an assertion about the HTTP status code the caller saw. Also run against a full real stack, not only the test suite: real `nia-api`, `nia-gateway`, and `Tessera.Service` processes, a real Postgres backing the shared credential and audit stores, and a real standalone HTTP server standing in for the downstream tool, logging every request it received to a file outside the gateway's own process. A valid credentialed call reached it once and got its actual JSON response back; killing the agent afterward and retrying the same credential produced a 401 with the downstream's request log unchanged, zero additional lines, confirming live, not just in a mock, that a killed agent's alternate path to the real tool doesn't exist.

What this doesn't cover, named plainly: full content inspection or semantic detection of a subtly poisoned but well-formed downstream response, MCP protocol semantics beyond a plain JSON request/response (no streaming, no multi-step MCP handshake, this proves the enforcement-then-forward mechanism, not a complete MCP client), and per-tool downstream routing, see the simplification above. See docs/THREAT_MODEL.md's rewritten threat 6 for the full reasoning on what detecting a compromised downstream tool does and doesn't mean now.

### Tamper-evident audit

Before this pass, `internal/audit` was an honest record of what happened, but nothing about it proved the record hadn't been changed since. Anyone with write access to the underlying store, `InMemorySink`'s process memory or `PostgresSink`'s `audit_events` table, could edit, delete, insert, or reorder rows and the trail would look exactly as clean afterward as it did before, `Recent` and `ForAgent` just read back whatever is currently there.

`internal/audit/chain.go` adds a hash chain: every event, when it's appended, gets a hash computed from its own canonicalized data plus the previous event's hash, and both the hash and the prev_hash it chained from are stored alongside it. `canonicalize` fixes field order explicitly rather than trusting `encoding/json`'s (stable in practice, not a contract) and truncates the timestamp to microsecond precision, the same precision `TIMESTAMPTZ` actually stores, found the hard way during verification: without the truncation, every event looked "modified" the instant it was read back from Postgres, not because anything was tampered with, only because Postgres rounds a `time.Time`'s nanosecond remainder on insert and the untruncated hash computed at write time could never agree with what got recomputed from the rounded value at read time. `GenesisHash`, sixty-four zero characters, is the defined prev_hash for the first event in a chain, a documented constant rather than an empty string standing in ambiguously for "unset."

`Verify(ctx, store)` walks a chain in the storage layer's own append order (Postgres's `id`, not the caller-supplied `at`) and recomputes every hash independently from the stored data, it never trusts anything the writing process claimed. It catches all four named tampering shapes, though three of them collapse to the same underlying check: a modified event fails its own recomputed-hash comparison directly; a deleted, inserted, or reordered event each leave a gap between one event's prev_hash and its actual predecessor's hash, a single "prev_hash doesn't match" check catches all three, because from the read side they look the same, a break in the linkage between two consecutive entries, see `chain_test.go`'s `TestVerify_DetectsDeletedEvent`, `TestVerify_DetectsInsertedEvent`, and `TestVerify_DetectsReorderedEvents` for one of each, constructed differently but caught the same way. `VerifyResult` reports `Checked`, `Skipped` (events with no hash at all, see below), and a `Breaks` list naming exactly which event and why, not just a pass/fail bool, an operator running this needs to know where to look, not just that something's wrong.

Both `InMemorySink` and `PostgresSink` implement `Chained`, the narrow read interface `Verify` needs. `InMemorySink` tracks its own running hash in memory; because it evicts events past its capacity, its `Chain()` reports `StartsAtGenesis: false` once eviction has happened, so `Verify` doesn't mistake routine capacity-bounded eviction for a broken genesis link. `PostgresSink` adds `hash` and `prev_hash` columns via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, the "first thing to replace" `schemaSQL`'s own comment named the day this table's shape needed to change, and a new singleton `audit_chain_state` table holding the running last-hash. `Append` now runs inside a transaction that does `SELECT last_hash FROM audit_chain_state ... FOR UPDATE` before inserting, locking out any other concurrent writer, including a different process sharing this database, until commit, which is what keeps the chain correct under the exact concurrent-writer reality this codebase already has, `cmd/api` and `cmd/gateway` both appending to one shared audit database once `NIA_AUDIT_DATABASE_URL` is set, not just correct in a single-process test. A row written before this migration ran keeps `hash` and `prev_hash` empty forever, `Verify` reports those as `Skipped`, explicitly excluded rather than either trusted or flagged, there was never a hash computed for them to check against, and the first genuinely chained row after the migration correctly requires a real genesis link regardless of how many unhashed legacy rows sit before it in the table, because `audit_chain_state` is seeded fresh at construction, independent of what `audit_events` already contained.

`GET /audit/verify` (`niactl audit verify`) is the verification operation itself: `cmd/api/main.go`'s `handleVerifyAudit` type-asserts `s.auditLog` to `audit.Chained` (both stores this codebase ships satisfy it, a future `Sink` that doesn't returns 501 rather than panicking or silently claiming a chain it never checked) and returns the full `VerifyResult` as JSON.

Verified two ways, same discipline as every other pass in this document. `internal/audit/chain_test.go` covers `Verify`'s own logic directly, an untampered chain, the genesis rule, all four tampering shapes, the pre-chain-skip case, and the eviction case, against `InMemorySink` and a hand-built `fakeChainedStore`. And, because this feature exists specifically to be trusted independent of the application, `internal/audit/postgres_sink_live_test.go` runs the same five proofs with real SQL against a real Postgres table, not a simulated tamper against an in-memory struct: `UPDATE`, `DELETE`, a forged `INSERT` reusing a freed id (a plain `INSERT` can't land between two contiguous `BIGSERIAL` ids, the same constraint a real attacker with ordinary table access would hit), and a same-id content swap for reordering. Also run against the full real stack outside the test suite: real `nia-api` and `nia-gateway` processes sharing one Postgres audit database, a mixed chain of registration, grant, credential, a real gateway-authorized tool call, and a kill, `niactl audit verify` reporting `OK:true` across all five events written by both processes together, then a direct `UPDATE` against the gateway's own `gateway.allowed` row (written by the *other* process from the one `niactl` was talking to) and `niactl audit verify` catching it by name, `"Seq":106` naming that exact row, over the real CLI surface, not just in a test.

The security boundary, stated once here and repeated in `chain.go`'s own doc comment because it needs to be understood by anyone reading a verification result, not just anyone reading the code:

> Hash chaining provides tamper evidence.
> It does not by itself prevent a privileged database administrator
> from rewriting both the events and the chain.

An attacker who modifies, deletes, inserts, or reorders events without also correctly recomputing every hash after the point they touched gets caught, that's the overwhelmingly likely case: `TestVerify_DetectsInsertedEvent` and its live-Postgres counterpart both show the forged event's own hash checking out fine, since the algorithm is public and self-consistency is cheap to fake, what catches it is the next real event downstream still pointing at the original hash. An attacker who rewrites the entire chain's suffix consistently after their tamper, or who has the access to just replace the whole table, hash column included, is not caught by anything in this file, that would need an external anchor the database itself can't rewrite, a periodic signed checkpoint published somewhere else, or WORM storage for the table. Neither exists yet. `Chained` is deliberately the narrow interface such a checkpoint mechanism would need (read the current chain state), so adding one later means adding a second consumer of this API, not redesigning it.

### Structured incident evidence

`internal/audit` answers "what happened": a chronological line per decision, `gateway.denied`, `monitoring.kill`, tied together only by an operator-supplied free-text `Incident` string if one was even passed. `internal/incident` answers a narrower, more specific question: for one containment decision, what triggered it, exactly. Every time `internal/monitoring.Monitor.Observe` flags, revokes, or kills, and an `incident.Store` is configured, it also creates one `Incident` record: the agent, the correlator string (the same one that ends up in the audit event's `Incident` field), the action taken, the risk value of the call that tipped it over, the cumulative total at that moment, the exact signals that made up the score, and the reason string. One record per decision, not a description reconstructed later by grepping the audit trail for lines that happen to share an incident string.

This still doesn't carry a blast-radius snapshot from the identity graph, see the package's own doc comment for why: an `Incident` record is written the moment `Monitor.Observe` decides, and wiring in a `GET /graph/{ref}/blast-radius` call there would mean `internal/monitoring`, which runs inside `cmd/gateway`, reaching back into `cmd/api` over HTTP mid-decision, a real dependency this pass didn't want to add to the containment path itself. The graph is populated automatically now, see "The identity graph" above, and `niactl simulate attack` reads a scenario's blast radius back right after the run to show it's real, but an `Incident` record and a blast-radius snapshot are still two separate reads, not one payload.

Records are created inside `internal/monitoring`, which only ever runs inside `cmd/gateway`, so that's also where they're read back from: `GET /incidents` (optionally `?ref=` and `?limit=`) and `GET /incidents/{id}`, not `cmd/api`. `niactl incident list` / `get` talk to the gateway's address (`NIA_GATEWAY_URL`) for exactly that reason, the same way `niactl gateway call` and `niactl simulate attack` already do. The store behind it is the in-memory reference implementation today, process-local, not shared across gateway replicas, no persistence across a restart, the same limitation as every other in-memory store in this codebase, and unlike `internal/audit` there's no `PostgresSink`-equivalent yet, a real deployment running more than one gateway instance would need one before this is more than a single-process convenience, tracked as an open gap rather than solved by rushing a shared backend into this pass.

### Metrics

`GET /metrics` on both `cmd/api` and `cmd/gateway` serves Prometheus text exposition format, `internal/metrics`, hand-rolled rather than a dependency on `github.com/prometheus/client_golang`. This codebase has exactly one external dependency today, `lib/pq`, and only when `NIA_AUDIT_DATABASE_URL` is set; Prometheus's own text format is a handful of plain lines per metric, not a reason to pull in a real client library for the counters and gauges each process actually needs. If this ever grows into needing histograms, summaries, or a pull-based exporter with more machinery than a registry and a text writer, that's the trigger to switch, not something to build ahead of time here.

Every counter is named to match an existing `internal/audit` action or `docs/SECURITY_INVARIANTS.md` invariant, so a metric and an audit event or invariant describe the same thing two different ways rather than inventing a second vocabulary. `cmd/api` exposes `nia_agent_registrations_total{result}` and `nia_tool_registrations_total{result}` (`created`/`duplicate`/`error`, `duplicate` broken out on its own because invariant 7 treats an actual duplicate as a distinct, expected outcome, not a backend failure), `nia_credentials_issued_total{result}` and `nia_credentials_revoked_total{result}` (`success`/`error`), `nia_grants_written_total{result}` (`success`/`killed`/`error`, `killed` when `WriteGrants` returns `policy.ErrKilled`), `nia_grants_deleted_total{result}` and `nia_kills_total{result}` (`success`/`error`), `nia_audit_write_failures_total` and `nia_graph_write_failures_total{op}` (`add_node`/`add_edge`), which make the fail-open postures invariants 8 and 9 describe observable over HTTP for the first time, previously nothing surfaced them beyond a log line, and two gauges, `nia_agents_registered` and `nia_tools_registered`, evaluated at scrape time off the same `List()` calls `GET /agents` and `GET /tools` already make.

`cmd/gateway` exposes `nia_gateway_requests_total{outcome}` (`allowed`/`denied_tool`/`denied_resource`/`unknown_tool`/`tool_lookup_error`/`check_error`/`resolve_error`/`unresolved`), one Inc per `handleToolCall` outcome, covering every branch from a resolver failure through the tool-level and resource-level checks to the final allow; `nia_monitoring_actions_total{action}` (`flag`/`revoke`/`kill`), incremented only when `Monitor.Observe` actually took a containment action, not on every scored call, `nia_gateway_requests_total{outcome="allowed"}` is already "how often was a call scored" since every allowed call gets scored when monitoring is configured; and its own `nia_audit_write_failures_total`, the same invariant as `cmd/api`'s counter of the same name, a separate count because each process keeps its own audit sink.

`GET /agents/{ref}` on `cmd/api` is the one direct agent-identity lookup that was missing before this pass, everything else about an agent (grants, credentials, audit history, graph reachability) already had its own sub-resource endpoint. `GET /risk/{ref}` on `cmd/gateway` exposes what `internal/monitoring.Monitor` already tracks internally but never surfaced over HTTP: the agent's current cumulative risk (`Monitor.CumulativeRisk`), the flag/revoke/kill thresholds it's being compared against (`Monitor.Thresholds`, new accessor), and, when an `incident.Store` is configured, its most recent incident records. When the gateway has no `Monitor` configured at all, the response says so plainly (`"configured":false`) rather than returning a zero cumulative that would look identical to an agent with a genuinely clean history.

`niactl agent inspect -ref <agent_ref>` composes all of this into one operator-facing report: identity, credentials, grants, recent audit (most recent first, client-side truncated, `GET /agents/{ref}/audit` has no limit param of its own), blast radius, and a best-effort call to the gateway's `GET /risk/{ref}`, best-effort because the gateway is a separate process and monitoring on it is opt-in, an unreachable gateway or unconfigured monitoring there is routine, not a failure of the inspect command. `niactl risk -ref <agent_ref>` is a thinner wrapper, it just prints `GET /risk/{ref}`'s raw response, the same convention `niactl incident list`/`get` already use for gateway-side reads.

### Integration plan for Tessera

Tessera started as a .NET library plus reference in-memory implementations. Its own roadmap listed what NIA needed from it: a minimal HTTP surface for kill, restore, and onboard (v1.2), and an OpenFGA REST adapter with paging and chunking (v1.1). Rather than reimplementing Tessera's invariants in Go, the plan was to finish that roadmap as part of standing NIA up, since NIA is the first real consumer of exactly that surface. That plan is done:

1. Built the REST adapter for `IAuthorizationStore` in Tessera (v1.1), talking to OpenFGA's plain HTTP API rather than the official SDK. This is what lets Tessera talk to a real OpenFGA instance instead of the in-memory reference store.
2. Built the minimal HTTP surface in Tessera (v1.2): onboard, kill, restore, and a read (`GET /clients/{client_ref}`, added once NIA's own client needed a way to read current state before writing to it), all behind a hand-rolled HS256 bearer auth gate. This turned Tessera from a library you embed into a service NIA can call over HTTP.
3. `internal/policy/tessera_client.go` in NIA is that REST client: `TesseraHTTPClient` implements the same `Client` interface `InMemoryClient` does. WriteGrants and DeleteGrants do a read, merge, then a full onboard, since onboard is Tessera's only mutation route and it's full-state reconcile, not incremental. Kill calls kill. Restore calls restore.
4. The gateway still calls OpenFGA directly for the actual per-request check, same as Tessera's own architecture, so authorization stays off the hot path. `TesseraHTTPClient.Check` exists for the control plane's own use (inspection, niactl, that kind of call), not the gateway's hot path, and it reads Tessera's declared grant state, not live OpenFGA truth, see the type's own doc comment for why those two aren't always the same thing right after a kill and restore.

Both implementations of `Client` (`InMemoryClient`, `TesseraHTTPClient`) live in `internal/policy`, verified against each other's own test suite plus a cross-language smoke test (`internal/policy/tessera_client_live_test.go`) that spawns a real `Tessera.Service` process and drives it over actual HTTP, the same live-process pattern Tessera's own `tools/ServiceHarness` uses. That live test is what caught a real bug during this work: a client-side optimization that skipped re-declaring grants Tessera already had on file, which looked safe until the live test showed a kill followed by a restore leaves the declared grant list untouched while clearing the actual OpenFGA tuples, so skipping the redeclare silently left the agent unauthorized while every read-only call still reported it as granted. Fixed by always calling onboard on a `WriteGrants` call against a known agent, not just when the requested grants are new. Known gaps that remain, all documented in `TesseraHTTPClient`'s own comment rather than left implicit: the read-modify-write only serializes within one client instance, not across replicas (needs Tessera's own database advisory lock, still on its roadmap); most calls other than Kill authenticate as a configured system identity rather than a real per-operator one, since `Client.Restore` and the others carry no operator parameter to sign with; and `business_unit` can be preserved through this client but never set by it, nothing in `Client` carries it.

`cmd/api` and `cmd/gateway` pick which `Client` to run against at startup (`policy.FromEnv`, `internal/policy/from_env.go`), `NIA_TESSERA_BASE_URL` unset keeps the in-memory default, setting it and the shared signing key alongside it switches to `TesseraHTTPClient`. That in-memory default is per-process, not shared, worth stating plainly since it is easy to assume otherwise: `cmd/api` and `cmd/gateway` are two separate binaries, and with `NIA_TESSERA_BASE_URL` unset each one constructs its own private `InMemoryClient`, so a grant written through `cmd/api`'s HTTP surface is invisible to `cmd/gateway`'s own check, every call comes back denied for a genuinely empty reason, not a bug in the check itself. Every command in this repo other than `gateway call` and `simulate attack` talks only to `cmd/api`, so the in-memory default is fine for them, those two specifically need `cmd/api` and `cmd/gateway` pointed at the same `TesseraHTTPClient` backend to see each other's grants, see "Running locally" in README.md for the exact setup, Tessera's own `InMemoryAuthorizationStore` fallback is enough for that, no live OpenFGA required. Wiring that in surfaced a second real bug, this one only visible with an actual `cmd/api` process talking to an actual `Tessera.Service` process, not from either side's own test suite: NIA's own agent ref convention is type-prefixed (`agent:billing-reconciler`, see `identity.AgentRef.Ref`), and Tessera's `CanonicalForm.ClientRef` rejects `:` outright, so every single call failed with "client_ref contains an invalid character" the moment a ref in NIA's actual shape crossed the wire, something no unit test caught because none of them used a colon-bearing ref. Fixed with a reversible, collision-free escape at the `TesseraHTTPClient` boundary (`encodeClientRef`/`decodeClientRef`), confirmed against the real service the same way the first bug was: a register, a kill, and a direct read of Tessera's own state afterward, over real HTTP, through `cmd/api`, not a mock.

`deployments/docker-compose.yml` wires all four services (`nia-api`, `nia-gateway`, `tessera`, `openfga`, plus `postgres`) together, with Dockerfiles for `cmd/api`, `cmd/gateway` (this repo), and `Tessera.Service` (the Tessera repo), and it has actually been run: all five containers built and came up healthy, and `deployments/bootstrap-openfga.sh` creates the OpenFGA store and authorization model Tessera needs to point at it, the manual step docker-compose can't do on its own since a store only gets an id once OpenFGA is already up. With that in place, a client was onboarded through Tessera's real HTTP surface, checked as allowed directly against OpenFGA, killed, and checked again as denied, real tuples written and deleted in a real OpenFGA store, not the in-memory one Tessera used in every check up to this point.

That run caught two more real bugs, both in Tessera's OpenFGA adapter, both only reachable by pointing it at a real store. `Program.cs` registered `IAuthorizationStore` with `AddHttpClient<IAuthorizationStore, OpenFgaAuthorizationStore>(...).AddTypedClient(factory)`, and `AddTypedClient`'s type parameter is inferred from the factory delegate's return type, not carried over from the call it's chained onto, so it silently bound the factory to the concrete `OpenFgaAuthorizationStore` type instead of the `IAuthorizationStore` interface everything else asks for. A request for `IAuthorizationStore` fell through to `AddHttpClient`'s own default factory, which tries to construct `OpenFgaAuthorizationStore` through the container and can't resolve its plain `string storeId` constructor argument, throwing the moment anything actually used the store. Fixed with an explicit `AddTypedClient<IAuthorizationStore>(...)`. Second, `OpenFgaAuthorizationStore.ReadTuplesForClientAsync`, which both `ClientProvisioner`'s reconcile diff and `KillSwitchService`'s read-delete loop depend on, filtered OpenFGA's `/read` endpoint by `user` alone. Real OpenFGA rejects that outright, "the object type field is required", it has no query shape for "everything this user touches regardless of type", only the in-memory store tolerated that. Fixed by reading each of the two object types Tessera ever writes against, `api_group` and `api_endpoint`, one at a time with the type-only object filter, and merging the results. Neither bug was reachable by the harness tests or by the earlier live test against Tessera's in-memory store, both are in Tessera's own history on `feature/openfga-http-adapter`, right after the Dockerfile commit.

### What this scaffold is, and isn't

This started as architecture and a repo skeleton: package boundaries, the interfaces each package exposes, and enough scaffolding that `go build` and `go vet` pass clean, with in-memory reference implementations standing in for everything. It is still not a working implementation of all seventeen items, but four pieces have moved past that: the policy client (see "Integration plan for Tessera" above, both against Tessera's in-memory store and a real Tessera-plus-OpenFGA-plus-Postgres stack), the kill switch bridge (the same integration, `Kill` deletes real tuples), the audit trail's write path (the gateway writes every decision, allow, deny, check error, to `internal/audit`, not just `cmd/api`'s own registration and kill events, and both are queryable over HTTP and through `niactl audit`), and the audit trail's storage: `internal/audit.PostgresSink` is a second `Store` implementation, `database/sql` plus `lib/pq`, that `audit.FromEnv` picks when `NIA_AUDIT_DATABASE_URL` is set, and `docker-compose.yml` points both NIA services at the stack's own `postgres` service. Confirmed against a real stack, not just unit tests: registered an agent through `nia-api`, denied a gateway call against it, killed it, then read `nia-api`'s own `GET /agents/{ref}/audit` back and got all three events in order, `nia-api` and `nia-gateway` reading and writing the same table, which is the entire reason this piece exists, see README.md's Status section for the full sequence. Credential issuance and revocation (`internal/credentials`) and tool registration (`internal/registry/tools`) are wired the same way now, real endpoints and `niactl` commands, real tests, not just an interface and an in-memory struct nothing else calls. The gateway also now checks a tool against that catalog before ever reaching the policy check, when `NIA_TOOLS_API_URL` is set, see the MCP integration row above for why that lookup goes over HTTP back to `cmd/api` rather than a second shared store. Risk scoring and runtime monitoring moved past their own stubs too: `HistoryScorer` produces a real, if simple, score off novel-tool, tool-risk-class, and now sensitive-resource signals, and `internal/monitoring.Monitor` acts on it, flag, revoke, or kill, all the way through to `internal/policy.Kill` for the kill case. The identity graph is wired the same way now too, `POST /graph/nodes` and `/graph/edges` plus the neighbors, reachable, and blast-radius queries, and `niactl graph`, but it's still bookkeeping the graph itself answers questions about, not something `internal/policy` or the gateway's live check consults yet, a `trusts` or `delegates_to` edge doesn't change what OpenFGA allows, see the Agent-to-agent trust and Delegation rows above. The graph also isn't empty by default anymore, agent registration, tool registration, credential issuance, and grant writes all populate it as they happen, so `GET /graph/{id}/blast-radius` has something real to summarize the first time it's queried, not just after someone hand-builds the graph, see "The identity graph" above for the one gap that comes with it, a revoked grant's edge isn't removed yet. The gateway's argument inspection closes a related but different gap: an agent authorized to call a tool can now still be denied a specific resource that call's arguments touch, when that resource is classified sensitive and the agent lacks the matching `data` grant, see "Resource sensitivity" above, this is enforcement, not just bookkeeping, `policy.Check` is genuinely consulted a second time with a `GrantForData` grant. Risk scoring moved from judging each call in isolation to a running per-agent total that a kill resets and nothing else does, see the Runtime monitoring row above, and the gateway's response now surfaces that total and whatever action it triggered rather than the caller having to separately ask. Permissions had a real gap closed too: `internal/policy.Client.WriteGrants`/`DeleteGrants`/`ListGrants` existed from early on but were never reachable over HTTP, so there was no way to actually grant an agent anything through the running system, `cmd/api`'s new grants endpoints and `niactl grant` close that. `niactl simulate attack` is the first thing in this repo that exercises the whole loop end to end through real processes, agent registration, grants, gateway calls, risk accumulation, and (when monitoring is configured) an actual kill and the subsequent real denial, see "Attack simulation" above; it is a CLI-driven test harness for the live system, not a second implementation of any of it. Structured incident evidence is new too: every flag, revoke, or kill decision now produces an `internal/incident` record, the risk value, signals, and cumulative total that actually triggered it, not a description reconstructed later from the audit trail, see "Structured incident evidence" above for the honest gap that comes with it (no blast-radius snapshot yet, no shared backend across gateway replicas). CENTIPEDE's actual anomaly detection replacing `HistoryScorer` is still just an intent, not code.

Two small correctness bugs found during a security-invariants review are fixed now too, both in `cmd/api/main.go`: `handleKill` used to discard the local registry's `SetState` error after a policy-level kill succeeded, so a failure there could leave the registry silently reporting an agent as active that Tessera/OpenFGA had actually killed, with no log line, nothing; it now logs that failure instead, still without blocking the kill response, the kill itself is what matters. And `handleRegisterAgent`/`handleRegisterTool` used to map every error from `Register` straight to 409 Conflict without checking it was actually a duplicate, harmless while the in-memory implementations only ever returned that one error, wrong the day either is backed by something real that can fail other ways; both now check the specific sentinel error first and return 500 for anything else. See `docs/SECURITY_INVARIANTS.md` for both, plus three fail-open postures, audit writes, graph auto-population, and incident records, that were previously only described in prose and are now backed by tests that actually fail the write and confirm the action they were recording still succeeds.

This scaffold had no observability surface at all until this pass, no way to ask either process "how much traffic, how many denials, how many fail-open writes have actually happened" without grepping the audit trail by hand. `GET /metrics` on both processes and the counters and gauges behind it (see "Metrics" above) close that, along with the two lookups that were missing before an operator could act on what those counters show: `GET /agents/{ref}` on `cmd/api`, and `GET /risk/{ref}` on `cmd/gateway`, which finally exposes `Monitor.CumulativeRisk` outside the process that computes it. `niactl agent inspect` and `niactl risk` are the CLI surface for both, the first command in this repo that reads across every resource an agent touches (identity, credentials, grants, audit, blast radius, and gateway-side risk) into a single report instead of one resource per command.
